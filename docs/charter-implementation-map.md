# Карта: принцип Хартии → код → тест

Зачем этот документ: чтобы разговор о Хартии был инженерным, а не
спором о словах. Для каждого принципа видно, **где он живёт в коде**,
**чем доказан** и **что ещё не сделано**.

Статусы: ✅ работает и проверено · 🟡 частично · ⛔ не реализовано.

---

## 1. Вклад — это подтверждённый результат, а не активность

| | |
|---|---|
| **Принцип** | Поток начисляется за принятый результат, а не за «сидел online» |
| **Код** | `src/core/tasks/service.ts` (submit → accept), `src/core/reports/`, `src/core/otc/` |
| **Проверка** | `scripts/test-tasks.ts` — отчёт с артефактом, приёмка, ровно один Поток |
| **Статус** | ✅ |

Что обсуждать: какие ещё виды вклада считать подтверждаемыми (ревью,
наставничество, документация) и как их измерять, не превращая в «часы».

---

## 2. Проверка не зависит от доброй воли проверяющего

| | |
|---|---|
| **Принцип** | ОТК не проверяет свою работу; критерии обязательны; просрочка эскалируется |
| **Код** | `src/core/tasks/service.ts` (I.2.12), `src/core/otc/service.ts`, `otc_criteria`, `otc_escalations` |
| **Проверка** | `test-tasks` (409 без критериев), `test-otc`, worker `escalateOverdue` |
| **Статус** | ✅ (SLA 24 ч, эскалация раз в час) |

Что обсуждать: кто утверждает критерии для нового направления и можно ли
менять критерии задним числом.

---

## 3. Пересмотр решения — процедура, а не произвол

| | |
|---|---|
| **Принцип** | Принятый результат можно пересмотреть с причиной; Поток отменяется |
| **Код** | `reopenTaskService`, `otc_escalations`, `otc_appeals` |
| **Проверка** | `test-tasks` (reopen → net 0 → повторная приёмка = 1 Поток) |
| **Статус** | ✅ |

Что обсуждать: сколько раз можно пересматривать одну задачу и кто платит
за пересмотр (время проверяющих — тоже ресурс).

---

## 4. Поток ≠ деньги ≠ власть

| | |
|---|---|
| **Принцип** | Подтверждённый вклад не даёт автоматически доступ к казне |
| **Код** | `src/core/flows/` (репутация) и `src/core/treasury/` (деньги) — разные модули; `APPROVER_ROLES` |
| **Проверка** | `test-invariants` — OTC не подписывает казну, одна подпись не тратит |
| **Статус** | ✅ |

Что обсуждать: можно ли Поток обменивать на что-то материальное, и если
да — не станет ли он скрытой валютой.

---

## 5. Мандат срочный и отзываемый

| | |
|---|---|
| **Принцип** | Роль — временное полномочие; истекает, ротируется, отзывается |
| **Код** | `src/core/mandates/`, `src/core/council/service.ts` (ротация 180 дней), `participant_roles.valid_to` |
| **Проверка** | `test-council`, `test-invariants` (истечение, отзыв, повторная выдача) |
| **Статус** | ✅ |

Что обсуждать: что происходит с человеком после истечения мандата —
остаётся ли он в ячейке, теряет ли доступ к панели.

---

## 6. Казна: пол и коллективное решение

| | |
|---|---|
| **Принцип** | Пол 1.00, траты 3 из 5, выкуп по курсу, прибыль 60/30/10 |
| **Код** | `src/core/treasury/service.ts`, `db/migrations/042…052` |
| **Проверка** | `test-treasury` (genesis, сплит, 3 подписи, пол, выкуп, дар) |
| **Статус** | ✅ |

Что обсуждать: что считается «общим благом» и кто ведёт список того,
на что казна тратится.

---

## 7. Шлюз: разделение полномочий и устойчивость

| | |
|---|---|
| **Принцип** | Создать сделку ≠ одобрить ≠ провести деньги; гонки не задваивают |
| **Код** | `src/core/gateway/`, `src/core/treasury/recordGatewayRevenue` |
| **Проверка** | `test-gateway-contour` (403 внешнему, 409 до одобрения, гонка 200+409, 60% один раз) |
| **Статус** | ✅ |

Что обсуждать: кто такой «внешний аудитор» и как он получает мандат.

---

## 8. Ячейки: 5×5 и готовность

| | |
|---|---|
| **Принцип** | Ячейка без плана, координатора и ОТК не работает |
| **Код** | `src/core/cells/` (`readiness.ts`), `plans.cell_id`, `cells.status` |
| **Проверка** | `test-capacity-cells` (нет состава/плана → не готова; полный состав + план → готова) |
| **Статус** | ✅ |

Что обсуждать: обязателен ли ОТК внутри ячейки или достаточно внешнего.

---

## 9. Ёмкость: люди считаются до старта

| | |
|---|---|
| **Принцип** | Сначала прогон «сколько нужно / сколько есть», потом задачи |
| **Код** | `src/core/capacity/` (`/capacity`), `participant_competencies` |
| **Проверка** | `test-capacity-cells` |
| **Статус** | ✅ (базовый расчёт) |

Что обсуждать: как оценивать «норму» на задачу, чтобы дефицит не был
фикцией.

---

## 10. Ученик — учитель — ученик

| | |
|---|---|
| **Принцип** | Передача опыта — часть работы, а не «общественная нагрузка» |
| **Код** | `src/core/mentors/` (`integrator_mentors`), `src/core/questions/` |
| **Проверка** | `test-questions` (нельзя отвечать себе, SLA, эскалация) |
| **Статус** | 🟡 наставничество есть как реестр, но не как роль в ячейке |

Что обсуждать: должен ли наставник получать Поток за ученика, и как
измерить «научил», а не «отсидел».

---

## 11. Сбой — сигнал, а не разговор

| | |
|---|---|
| **Принцип** | Не справляются → сигнал с уровнем L0–L3 и решением |
| **Код** | `src/core/cells/reassignment.ts`, `reassignment_signals` |
| **Проверка** | `test-reassignment` (L0→L3, запрет выше, resolve/reject) |
| **Статус** | ✅ (ручное поднятие; автосигналы — следующий шаг) |

Что обсуждать: кто имеет право закрыть сигнал L2 без Совета.

---

## 12. Прозрачность и проверяемость

| | |
|---|---|
| **Принцип** | Любое решение можно восстановить: кто, когда, на каком основании |
| **Код** | `audit_log`, `access_log`, `criteria_snapshot`, `plan_versions` |
| **Проверка** | smoke-тесты аудита, `test-plan-versions` |
| **Статус** | ✅ |

Что обсуждать: что из аудита должно быть публичным, а что — только
для Совета.

---

## 13. Планы меняются процедурой

| | |
|---|---|
| **Принцип** | План версионируется; принятые задачи не отменяются молча |
| **Код** | `plans.version`, `plan_versions`, `POST /plans/:id/versions` |
| **Проверка** | `test-plan-versions` (v1 → v2 → restore как v3) |
| **Статус** | ✅ |

Что обсуждать: кто утверждает смену версии плана верхнего уровня.

---

## 14. Нология и право на остановку

| | |
|---|---|
| **Принцип** | Процесс можно остановить, но только с обоснованием |
| **Код** | ⛔ отдельного модуля нет; сигналы и Совет — есть |
| **Проверка** | — |
| **Статус** | ⛔ |

Что обсуждать: нужен ли отдельный институт Нологии в коде или достаточно
сигнала L3 с обязательным письменным обоснованием.

---

## Как пользоваться этой картой

- Спорите о принципе — сначала посмотрите, **как он уже реализован**.
- Предлагаете изменение — покажите, какой тест должен измениться.
- Нашли расхождение «в Хартии так, в коде иначе» — создайте issue
  с меткой `charter` и ссылкой на строку Хартии.

Карта живая: при изменении правила обновляйте и её.
