  name: api
  namespace: xartia
  labels: { app: api, xartia.io/tier: app }

  replicas: 1
  revisionHistoryLimit: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      serviceAccountName: api
      priorityClassName: xartia-critical
      # Ждём postgres-svc:5432 до старта api (RUN_MIGRATIONS=true).
      # Образ postgis уже в k3d (из Сессии 3), pull не нужен.

        - name: wait-for-postgres
          image: postgis/postgis:15-3.4
          imagePullPolicy: IfNotPresent
          command:
            - sh
            - -c
            - |
              until pg_isready -h postgres-svc -p 5432 -U charter; do
                echo "waiting for postgres-svc ..."

            requests: { cpu: "10m", memory: "32Mi" }

        - name: api

            - { name: http, containerPort: 3000 }

            httpGet: { path: /health/ready, port: 3000 }
            initialDelaySeconds: 15
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 3

            httpGet: { path: /health/live, port: 3000 }

## 13. k8s/base/postgres/backup-cronjob.yml

```yaml
# base/postgres/backup-cronjob.yml
# Ежедневный pg_dump → MinIO (S3). Retention 7 дней.
# НЕ путать с Velero (K8s-объекты, Сессия 9).
apiVersion: batch/v1
kind: CronJob
metadata:
  name: postgres-backup
  namespace: xartia-data
spec:
  schedule: "0 3 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      template:
        spec:
          priorityClassName: xartia-batch
          restartPolicy: OnFailure
          containers:
            - name: pg-dump
              image: postgis/postgis:15-3.4
              command:
                - /bin/sh
                - -c
                - |
                  set -e
                  ts=$(date +%Y%m%d-%H%M%S)
                  f=/tmp/charter-${ts}.sql.gz
                  pg_dump -h postgres-svc.xartia-data.svc -U charter -d charter | gzip > "$f"
                  mc alias set minio "$S3_ENDPOINT" "$S3_ACCESS_KEY" "$S3_SECRET_KEY"
                  mc cp "$f" minio/charter-archive/postgres-backups/
                  echo "OK: $f"
              envFrom:
                - secretRef: { name: postgres-secrets }
                - secretRef: { name: minio-secrets }
              resources:
                requests: { cpu: "100m", memory: "256Mi" }
                limits:   { cpu: "500m", memory: "1Gi" }
```

# 3 класса приоритета. Cluster-scoped (не в namespace).
#
# xartia-critical — api, ws, postgres, redis. Вытесняют всё остальное
#                   при нехватке ресурсов.

  name: xartia-critical
value: 1000000
globalDefault: false

apiVersion: scheduling.k8s.io/v1

  name: xartia-default

## 39. k8s/longhorn/README.md

```markdown
# Longhorn — распределённое блочное хранилище

## Почему Longhorn

- **CNCF incubating**, Rancher/SUSE.
- **Replicated block storage** — данные реплицируются между нодами участников.
- **Backup to S3** (наш MinIO) + **DR volume** (реплика в другом месте).
- **Снапшоты, restore, expansion**.
- Работает поверх любого диска (NVMe, HDD, USB).

## ⚠️ НЕ работает на k3d (Windows/macOS)

Longhorn требует **Linux-нод** (kernel modules, iSCSI). k3d на Windows/macOS — это Linux-VM внутри Docker, но iSCSI-модули не всегда доступны. На dev-кластере используем `local-path` (k3s default).

**Staging/prod — Linux-ноды (VPS, bare-metal, K8s на Linux-VM с iSCSI).**

## Установка (staging/prod)

```powershell
# 1. Добавить Helm-репозиторий
helm repo add longhorn https://charts.longhorn.io
helm repo update

# 2. Установить Longhorn в namespace longhorn-system (уже создан в base/)
helm install longhorn longhorn/longhorn `
  --namespace longhorn-system `
  --set defaultSettings.defaultReplicaCount=2 `
  --set defaultSettings.storageMinimalAvailablePercentage=15 `
  --set defaultSettings.backupTarget="s3://longhorn-backup@minio.xartia-data.svc:9000/" `
  --set defaultSettings.backupTargetCredentialSecret="longhorn-minio-credentials"

# 3. Дождаться готовности (3-5 минут)
kubectl -n longhorn-system get pods -w

# 4. Применить StorageClass'ы
kubectl apply -k k8s/longhorn/
Проверка:

powershell
kubectl get storageclass | Select-String longhorn
kubectl -n longhorn-system get pods
Ожидаемо: 3 StorageClass (longhorn-r1, longhorn-r2, longhorn-r3), все поды Longhorn в Running/Completed.

Что создаётся
StorageClass	Реплик	Использование
longhorn-r3	3	Postgres (prod), критичные данные
longhorn-r2	2	Redis, MinIO, backup (MinIO — свой erasure coding, но backup-каталог на Longhorn — RF=2)
longhorn-r1	1	Кэши, временные данные, логи
reclaimPolicy: Retain — критично
Все три StorageClass'а имеют reclaimPolicy: Retain. Это значит: kubectl delete pvc не удаляет данные — PVC переходит в Released, данные остаются на диске. Для Postgres это защита от случайного kubectl delete.

Восстановление после Retain:

powershell
# PVC остался, но Released. Пересоздать с тем же именем:
kubectl -n xartia-data delete pvc postgres-data-postgres-0
kubectl -n xartia-data apply -f postgres-statefulset.yml  # PVC пересоздастся
Backup (Velero + restic)
В Сессии 9. Longhorn сам умеет backup в S3 (MinIO), Velero — для K8s-объектов. Оба нужны.

Что НЕ входит в эту сессию
MinIO distributed — отдельно (Data layer, Сессия 3). MinIO использует свой erasure coding, не Longhorn.

Velero — Сессия 9.

Longhorn UI ingress — опционально, не критично.
```

# k8s/ — Kubernetes-манифесты XartIA

## Стратегия: base + overlays (C)

- **`base/`** — провайдер-agnostic. Namespaces, priorityclass, limitrange, resourcequota. **Никаких** `storageClassName`, `ingressClassName`, тегов образов, секретов.

- **`overlays/prod/`** — 3+ Linux-ноды. `longhorn-r3`, step-ca prod, 3 реплики, PDB, HPA.

## 74. k8s/worker/README.md

```markdown
# Cron-задачи XartIA (I.3.05.*)

Cron в XartIA — **децентрализован**. Единого планировщика в приложении нет.
Вместо этого:

- **Расписание** — в K8s CronJob (`k8s/worker/*.yml`).
- **Логика** — в HTTP-эндпоинтах API, защищённых `requireRight`.
- **Транспорт** — K8s CronJob дёргает эндпоинт через `curl` (или другой HTTP-клиент).

Это даёт:

- **Единый аудит** — каждая задача попадает в `audit_log` через обычный сервисный слой.
- **Отсутствие «магических» cron-скриптов** — вся логика в `src/core/*/service.ts`.
- **Простое тестирование** — можно вызвать эндпоинт вручную через `curl`/`pnpm tsx scripts/...`.
- **Горизонтальное масштабирование** — N реплик API + `concurrencyPolicy: Forbid` в CronJob гарантируют один запуск.

## Соглашения

### Именование

- **CronJob id** — `I.3.05.NN` (спецификация), дублируется в `metadata.labels.cron-id`.
- **Имя CronJob** — `<domain>-<action>[-<frequency>]`, напр. `psy-mood-aggregate-hourly`.
- **Namespace** — `xartia`.
- **Файл** — `k8s/worker/<domain>-<action>.yml`.

### Эндпоинт

- Метод: **`POST`** (даже если идемпотентно — единообразие).
- Путь: `/<domain>/<action>` — например, `POST /psy/mood/aggregate`.
- Права: **`requireRight('<resource>', 'Act')`** — «Act» — это доменное действие
  для машины. См. `C.0.01.06 FALLBACK_PERMISSIONS` и `rights_matrix`.
- Тело: JSON, обычно `{}` или `{ "period": "hour" }`.
- Ответ: JSON с полем `"errors": N` (0 — успех), остальное — диагностика.

### Аутентификация

CronJob логинится через `/auth/login` **сервисным участником** — каждая
задача имеет свой участник с ограниченной ролью. Пароль — в K8s Secret.

Не используйте:

- Личный токен Архитектора — TTL 15 минут, истёк → 401.
- Долгоживущие access-токены — их нет и не будет.
- Отключение auth на cron-эндпоинтах — открывает дверь для DoS.

### Образ

`curlimages/curl:8.10.1` — минимальный, ~2 MB, поддерживается.

### Hardening (стандартный набор)

```yaml
concurrencyPolicy: Forbid
activeDeadlineSeconds: 120        # или 180, если логика долгая
startingDeadlineSeconds: 300      # не запускать пропущенные >5 мин
backoffLimit: 2                   # 1 retry
successfulJobsHistoryLimit: 3
failedJobsHistoryLimit: 3
# + в контейнере:
securityContext:
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  runAsNonRoot: true
  runAsUser: 1000
```

### Создание сервисного участника

Пример для PSY-cron (PowerShell):

$password = -join ((48..57) + (65..90) + (97..122) | Get-Random -Count 32 | % {[char]$_})

# 2. Создать / обновить участника (идемпотентно).
pnpm tsx scripts/ensure-psy-cron.ts $password

# 3. Положить пароль в K8s Secret.
kubectl create secret generic xartia-psy-cron `
  --namespace xartia `
  --from-literal=phone='+70000000001' `
  --from-literal=password=$password
```

## Диагностика

### CronJob не запускается

```powershell
kubectl -n xartia describe cronjob psy-mood-aggregate-hourly
kubectl -n xartia get events --sort-by=.lastTimestamp | Select-Object -First 30
```

Типовые причины:

- **`no matches for kind "CronJob"`** — K8s <1.21, обновить или использовать `batch/v1beta1`.
- **`is forbidden`** — ServiceAccount, под которым запускается CronJob, не имеет прав
  на создание Pod'ов. Проверьте RBAC.
- **Схема некорректна** — `kubectl apply --dry-run=server -f <file>`.

### Job упал

```powershell
kubectl -n xartia get jobs
kubectl -n xartia logs job/psy-mood-aggregate-hourly-XXXXX
```

Ожидаемые строки:

```text
[cron] logging in as +70000000001
[cron] token acquired, calling /psy/mood/aggregate (period=hour)
[cron] response: {"processed":N,"created":M,"updated":K,"skipped":S,"errors":0,...}
[cron] OK
```

- **`[cron] ERROR: aggregate reported non-zero errors`** — смотри `"errors":N`
  в JSON. Значит API вернул 200, но внутри агрегации что-то падало
  (например, AVG на пустой выборке — но это не должно давать errors).

- **`login failed: HTTP 401`** — неверный пароль или participant удалён.
  Перезапустите `scripts/ensure-psy-cron.ts` и обновите Secret.

- **`login failed: HTTP 404`** — `/auth/login` не зарегистрирован.
  Проверьте `registerAuthRoutes(app)` в `src/server.ts`.

### Логи API во время cron

```powershell
docker compose -f docker/docker-compose.yml logs api --since 5m |
  Select-String "psy.mood.aggregate|psy_session"
```

Или в `audit_log`:

```sql
SELECT action, entity_type, entity_id, new_value, created_at
  FROM audit_log
 WHERE action = 'psy.mood.aggregate'
 ORDER BY created_at DESC
 LIMIT 10;
```

Ожидаемо: `actor_type = 'system'`, `new_value.processed = N`.

### Проверка, что агрегаты идут

```sql
-- За последние 24 часа должно быть ~24 записи (hourly) + 1 (daily).
SELECT date_trunc('hour', created_at) AS bucket,
       COUNT(*) AS records,
       MAX(value) AS max_value,
       MIN(value) AS min_value
  FROM mood_metrics
 WHERE created_at > now() - interval '24 hours'
 GROUP BY 1
 ORDER BY 1 DESC;

## 80. docker/entrypoint.sh

```bash
#!/bin/sh
# ─────────────────────────────────────────────
# XartIA API entrypoint
# Ожидает БД и Redis, опционально запускает миграции/seed
# ─────────────────────────────────────────────
set -e

log() {
  echo "[entrypoint] $*"
}

# ─── Ожидание PostgreSQL ───────────────────────
wait_for_postgres() {
  if [ -z "${DATABASE_URL}" ]; then
    log "DATABASE_URL not set, skipping postgres wait"
    return 0
  fi

  log "Waiting for PostgreSQL..."

  # Парсим хост и порт из DATABASE_URL
  DB_HOST=$(echo "$DATABASE_URL" | sed -n 's|.*@\([^:/]*\).*|\1|p')
  DB_PORT=$(echo "$DATABASE_URL" | sed -n 's|.*:\([0-9]*\)/.*|\1|p')

  DB_HOST=${DB_HOST:-localhost}
  DB_PORT=${DB_PORT:-5432}

  i=0
  until pg_isready -h "$DB_HOST" -p "$DB_PORT" -q; do
    i=$((i + 1))
    if [ "$i" -ge 60 ]; then
      log "PostgreSQL not ready after 60 seconds, giving up"
      exit 1
    fi
    log "  postgres is not ready yet ($i/60)..."
    sleep 1
  done

  log "PostgreSQL is ready"
}

# ─── Ожидание Redis ────────────────────────────
wait_for_redis() {
  if [ -z "${REDIS_URL}" ]; then
    log "REDIS_URL not set, skipping redis wait"
    return 0
  fi

  log "Waiting for Redis..."

  REDIS_HOST=$(echo "$REDIS_URL" | sed -n 's|redis://\([^:/]*\).*|\1|p')
  REDIS_HOST=${REDIS_HOST:-localhost}

  i=0
  until redis-cli -h "$REDIS_HOST" ping > /dev/null 2>&1; do
    i=$((i + 1))
    if [ "$i" -ge 60 ]; then
      log "Redis not ready after 60 seconds, giving up"
      exit 1
    fi
    log "  redis is not ready yet ($i/60)..."
    sleep 1
  done

  log "Redis is ready"
}

# ─── Миграции ──────────────────────────────────
run_migrations() {
  if [ "${RUN_MIGRATIONS}" = "true" ]; then
    log "Running migrations..."
    node_modules/.bin/tsx scripts/migrate.ts
    log "Migrations done"
  fi
}

run_seeds() {
  if [ "${RUN_SEED}" = "true" ]; then
    log "Running seeds..."
    # npm run seed
    log "Seeds placeholder (not implemented yet)"
  fi
}

# ─── Graceful shutdown ─────────────────────────
shutdown() {
  log "Received shutdown signal"
  if [ -n "${APP_PID}" ]; then
    kill -TERM "$APP_PID" 2>/dev/null || true
    wait "$APP_PID"
  fi
  exit 0
}

trap shutdown TERM INT

# ─── Main ──────────────────────────────────────
log "Starting XartIA API entrypoint"
log "  NODE_ENV=${NODE_ENV:-development}"
log "  LOG_LEVEL=${LOG_LEVEL:-info}"

wait_for_postgres
wait_for_redis
run_migrations

log "Starting application: $*"

# Запускаем приложение в фоне, чтобы ловить сигналы
"$@" &
APP_PID=$!
wait "$APP_PID"
```
