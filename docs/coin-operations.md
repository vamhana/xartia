# Монета XartIA: запуск, обслуживание, точки взаимодействия

**Статус:** рабочая документация. Что уже есть в коде — помечено ✅, чего нет — ❌.
Спецификация модели — `XartIA 5.0.md` (в папке `XartIA 4.2`).

---

## 1. Что это такое сегодня

Монета XartIA — **внутренняя учётная единица**, не токен на блокчейне.

| Свойство | Как устроено |
|---|---|
| Пол | **1.00 USD** — обеспечивается только T1 (USDC/фиат/T-bills) |
| Курс | `P = max(1.00, R / S)`, где `R = T1 + 0.5·T2` |
| Эмиссия | только genesis-депозит; дальше прибыль поднимает курс **без** выпуска |
| Траты | мультисиг **3 из 5**, только из премии, пол не трогается |
| Выкуп | по текущему курсу, но только если после выкупа `T1 ≥ S × 1.00` |
| Личные счета | ✅ `unit_accounts` — у каждого держателя (хартиец или «Вася») |
| Выплаты людям | ❌ нет: казна тратится сообща на общие блага |
| Внешние покупатели | ✅ любой может купить монету у протокола по курсу |
| Ключи | 5 ролей, ротация; счета пополнения — те же 5 ключей |
| Блокчейн | ❌ нет: учёт в БД, контракты 4.2 — отдельный архивный проект |

Проверяемость: страница **«Казна»** (`/treasury`) — T1, T2, R, выпуск, курс,
покрытие пола, подписанты, запросы трат, журнал операций.

## 2. Схема за один экран

```
Выручка Шлюза (500 USDC)
   │  POST /treasury/revenue  (или автоматически при audit сделки)
   ├─ 60% → T1 (резерв, пол)         300
   ├─ 30% → операционный счёт        150
   └─ 10% → буфер                     50

Курс: P = max(1.00, R / S)
   прибыль → R растёт → курс растёт (S не меняется)
   расход  → премия уменьшается → курс падает к 1.00, но не ниже

Трата (100 USDC на общие блага: серверы, юристы, инфраструктура):
   запрос → 3 подписи из 5 → проверка T1 − 100 ≥ S × 1.00 → исполнение

Внешний держатель («Вася»):
   USDC → покупка монеты по курсу (T1 растёт, S растёт, курс не меняется)
   монеты → дар казне (сжигаются, эквивалент уходит в операционный фонд)
   монеты можно держать и выкупить по полу/курсу
```

## 3. Как запустить

### 3.1. Предпосылки (без них запуск бессмысленен)

| Что | Зачем | Статус |
|---|---|---|
| Первый Архитектор | создаёт панели, подписывает, фолбэк | ✅ есть bootstrap |
| Совет направления 13 (Верификация) | подпись трат, контроль правил | ✅ выборы Совета |
| Совет направления 15 (Шлюз) | выручка и её конвертация | ✅ |
| Хранитель (внешний аудитор) | независимая подпись | ✅ роль KEEPER |
| Выборный делегат | представительство | ✅ Совет направления 9 |
| Банк/счёт T1 + USDC-кошелёк | реальное обеспечение пола | ❌ только учёт в БД |
| Юридическая обёртка | e-money/фонд, KYC/AML | ❌ не сделано |

### 3.2. Технический запуск (то, что уже работает)

```bash
pnpm install
pnpm db:migrate                 # 46 миграций, включая treasury (042) и панели (044–046)
pnpm tsx scripts/ensure-architect.ts
pnpm tsx scripts/seed-base.ts   # роли, направления, виджеты, панели, продуктовые панели
docker compose -f docker/docker-compose.yml up -d
pnpm tsx scripts/test-treasury.ts   # проверка казны: genesis, сплит, 3 подписи
```

Проверить, что казна пуста и готова:

```bash
curl -s localhost:3000/treasury/state -H "Authorization: Bearer $TOKEN"
# { t1Usdc: 0, supply: 0, price: 1, coverage: Infinity, ... }
```

### 3.3. Genesis (первый депозит)

Первый `POST /treasury/revenue` при `supply = 0` выпускает юниты ровно на
сумму в резерв по 1.00:

```
выручка 1000 USDC → T1=600, supply=600, цена 1.00
```

Это фиксирует пол и стартовое предложение. Дальше эмиссии нет.

### 3.4. Публикация

1. Открыть `/treasury` — проверить, что пол и покрытие видны.
2. Объявить участникам: курс, пол, правила трат, как проверять.
3. Включить уведомления: выручка и запросы трат приходят Совету
   (при отсутствии Совета — Архитектору).

### 3.5. Чего не хватает для «настоящего» запуска (честный список)

| Пробел | Что нужно |
|---|---|
| ❌ Реальное хранение T1 | банковский счёт + USDC-кошелёк, сверка |
| ❌ Ончейн-контракт 5.0 | контракт пола/NAV, аудит (4.2 — кривая, не подходит) |
| ❌ KYC/AML и юрлицо | до любого фиатного вывода |
| ❌ Автоматическая конвертация валюты | выручка в рублях → USD на входе |

## 4. Обслуживание: кто, что, когда

| Период | Действие | Кто |
|---|---|---|
| Ежедневно | новые сделки Шлюза → выручка в казну (автоматически при аудите) | Шлюз |
| Ежедневно | запросы трат: подписать/отклонить | 3 из 5 |
| Еженедельно | сверка T1: банк + USDC против `treasury_state` | Хранитель + Архитектор |
| Ежемесячно | отчёт: R, S, P, покрытие, операции; публикация | Совет + Хранитель |
| Каждые 180 дней | ротация Совета и подписантов | Архитектор |
| При инциденте | стоп операций, публичное уведомление, аудит | Архитектор + Хранитель |

### 4.1. Инциденты

| Событие | Действие |
|---|---|
| `T1 < S × 1.00` | **стоп** всех операций, публичный отчёт, аудит; пол не «печатаем» |
| T2 (USDT) обнулился | R падает на `0.5·T2`; пол не затронут; отчёт |
| Банк заморозил счёт | перевод T1 в другой банк; при нехватке — стоп |
| Массовый выкуп | пол 1.00 из T1; сверх пола — по ликвидности премии |
| Ошибка/взлом | пауза, форензика, T1 не выводится |

### 4.2. Проверки, которые уже автоматизированы

- `I.9.04.62` — smoke казны (genesis, сплит, 3 подписи, пол, выручка Шлюза, идемпотентность).
- `I.9.04.63` — smoke панелей (казна/Совет/надзор/Шлюз).
- 18 smoke-шагов в CI, 26 шагов локального прогона.

## 6. Правила и запреты

1. **Пол 1.00 неприкосновенен**: `T1 ≥ S × 1.00` проверяется на каждой операции.
2. **Траты — только 3 подписи из 5**; один человек — одна подпись.
3. **За монету нельзя купить Потоки, мандаты или голоса** — власть не следует из денег.
4. **Курс не гарантируется выше 1.00** — это NAV, а не обещание доходности.
5. **Публичность**: каждая операция — в журнале; каждая трата — с назначением.

---

## 7. Отчётность и налоги

- Каждая операция казны фиксируется: вид, сумма, курс, сделка Шлюза (если есть), автор.
- Для налогов: конвертация выручки — событие; хранить курс и сумму на дату.
- Ежемесячный отчёт: T1/T2/R/S/P/покрытие + операции + подписи.
