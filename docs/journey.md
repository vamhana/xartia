# Путь участника и путь сигнала — модель и слабые места

Документ отвечает на два вопроса: **что происходит с человеком** от заявки до
первой проверенной работы и **что происходит с идеей** от сигнала до стройки.
Каждый шаг размечен по факту: ✅ работает, 🟡 частично, ❌ нет.

Дата: 2026-10-24. Основание: Хартия 5.0 (части 1–6), текущий код и БД.

---

## 1. Путь участника

### 1.1 Регистрация → четыре функции

`POST /auth/register` создаёт заявку и **рассылает её четырём функциям**
(`C.0.02.02`). Если у функции в нужном направлении никого нет — уведомление
уходит Первому Архитектору (гарант процедуры, не начальник).

| Шаг | Кто действует | Что происходит в системе | Статус |
|---|---|---|---|
| 1 | человек с улицы | заявка `registration_requests.status='new'` | ✅ |
| 2 | **Инкубация** (Совет направления 11) | «Новая заявка: нужен аудит» → аудит, выбор направления и наставника | ✅ уведомление, 🟡 форма аудита не заполняется |
| 3 | **Балансировка** (`BALANCER`) | «+1 заявка» | ✅ |
| 4 | **Ноология** (`NOOLOG`, направление 6) | «Проверьте, правильные ли вопросы задаёт инкубация» | ✅ уведомление, ❌ нет самого набора вопросов в заявке |
| 5 | **Верификация** (`VERIFIER`, направление 13) | «Не бот ли» + доступ к аудиту | ✅ уведомление, 🟡 проверка вне системы |
| 6 | **Координатор** | координирует прохождение этапов | ❌ роли нет (Хартия 6.7/6.14), уведомления нет |

### 1.2 Приём

`POST /admin/registration-requests/:id/accept` → участник, пароль, welcome-задача,
роль (по желанию).

| Шаг | Что происходит | Статус |
|---|---|---|
| приём | `participants` + `participant_status_history` + welcome-задача | ✅ |
| роль при приёме | `S.0.01.03` через `assignRole` | ✅ |
| **куратор направления** получает «Новый участник — назначьте наставника» | `participant.accepted` | ✅ |
| балансировка «+1 участник» | `participant.balancing` | ✅ |

### 1.3 Наставник

| Шаг | Что происходит | Статус |
|---|---|---|
| выбор наставника | `GET /admin/mentors?direction_id=` — реестр `integrator_mentors` | ✅ |
| назначение | `PATCH /admin/participants/:id {mentor_id}` → `C.0.45.01`: реестр + `participants.mentor_id` | ✅ |
| наставник получает ученика | `mentor.assigned` с карточкой (имя, ID, ссылка) | ✅ |
| карточка ученика | `GET /admin/participants/:id/mentee-card`: задачи (всего/в работе/принято), Поток, наставник | ✅ |
| отдельный чат с учеником | `chat_channels` не создаётся автоматически | ❌ |
| Поток наставнику за проверенную работу | начисление по факту ОТК-приёмки работы ученика | ❌ |
| лимит учеников | 3 на наставника (I.6.4.1), проверяется | ✅ |
| балансировка «+ученик» | `mentor.balancing` | ✅ |

### 1.4 Дальше по пути

первая задача → отчёт с артефактом → ОТК → Поток → следующий уровень. Всё это
уже работает (см. `docs/product-v0.1.md`).

## 2. Путь сигнала: от идеи до стройки

Пример из жизни: участник пишет «есть опыт в играх, предлагаю сделать игру,
которая приносит деньги». Ниже — как это должно идти и что из этого есть.

| Этап | Смысл (стройка) | В системе | Статус |
|---|---|---|---|
| 1. Сигнал | прораб заметил: «нужен ещё один кран» | `signals` (тип, обоснование, приоритет, направления) | ✅ |
| 2. Префильтрация | диспетчер решает, кому | `C.0.10.02`: маршрутизация + уведомление Совета направления | ✅ |
| 3. Всеобщий прогон | совещание по объекту | `run`/`jury_session`/`responses` — ответы направлений | 🟡 обсуждение есть, «единого прогона» как экрана нет |
| 4. Решение | «строим микрорайон» | `plans.signal_id` — план вырос из сигнала | ✅ |
| 5. План | генплан: 20 домов, сроки, критерии | `plans` (title, expected_result, criteria, checkpoints, stop_conditions, подпись Хранителя) | ✅ |
| 6. Куратор | начальник участка | `plans.curator_id` — человек, а не направление; получает уведомление | ✅ |
| 7. Разбиение | 20 домов × (5 опытных + 15 учеников) | `plan_tasks` (plan → task, роль), `tasks.parent_task_id` | ✅ декомпозиция есть |
| 8. Ежедневные планы | наряд на день по каждому дому | `daily_plans` (направление, дата) + `daily_plan_tasks` | ✅ |
| 9. Исполнение | фундамент, стены, крыша | задачи со статусами, отчёты с артефактами | ✅ |
| 10. Сигналы с площадки | «на доме №7 бетон не тот» | новый сигнал от исполнителя | ✅ |
| 11. Прогресс и отклонения | дом №3 быстрее, дом №11 отстаёт | `C.0.06.03`: overdue/expected/breached → статус behind; балансировка видит список и одним действием поднимает сигнал направлению | ✅ |
| 12. Приёмка | комиссия | ОТК-решение → Поток | ✅ |
| 13. Итог | район сдан | план `completed`, Потоки распределены | 🟡 закрытие плана не автоматизировано |

### 2.1 Что уже связано (сделано 24.10)

- **Совет направления.** `C.0.46.01`: советник — самый опытный участник
  направления по числу принятых работ (каждая приёмка = Поток), с обязательным
  сроком мандата и ротацией, с возможностью дисквалификации (с причиной).
  Если опытных нет — функция ложится на Архитектора, и это видно в блоке
  «Совет направления». Сигнал, адресованный Совету, при его отсутствии уходит
  Первому Архитектору (C.0.10.02) — «в никуда» больше не уходит.
- **Дерево надзора (балансировка и Совет).** `C.0.06.06`: план → ветка →
  ячейка → человек. На каждом уровне: всего/принято/просрочено/сдано раньше,
  координатор (куратор плана, координатор ячейки), бейдж сигналов и кнопка
  «Сигнал Совету» прямо из узла. `signals.subject_*` (D.2.01.38) цепляют
  сигнал к плану, ветке или ячейке — поэтому «напротив дома сигнал» теперь
  рисуется. Совет видит то же дерево: может связаться с координатором ячейки
  или исполнителем.
- **Дерево работ.** `C.0.06.05`: план отдаётся деревом (рекурсивный запрос),
  страница `/plans/:id` — раскрытие веток как папок, карточка узла: статус,
  исполнитель, срок, «принято N из M» по поддереву. Микрорайон → дом → работа →
  человек: до каждого можно докопаться.
- **Передача наряда вниз (5 × 5).** `C.0.41.04`: координатор верхней ячейки
  делит наряд между дочерними ячейками; задача остаётся видимой на верхнем
  уровне (`delegated_to_cell_id`), но её ведёт дочерняя ячейка и раздаёт людям.
  На странице «Наряд» — блок «Передача в дочерние ячейки» и сводка по дочерним
  нарядам. Повторно передать ту же задачу нельзя (409).
- **Наряд ячейки.** `C.0.41.03`: наряд на дату на ячейку, распределение по
  участникам; назначать можно только участнику этой ячейки (403 иначе);
  страница `/naryad`. Координатор верхнего уровня раздаёт по ячейкам, каждая
  ведёт свой наряд.
- **Ветки плана.** `C.0.06.04`: у плана считаются параллельные участки
  (корневая задача + подзадачи) — «дом №1 сдан, дом №2 отстаёт». На панели
  балансировки блок «Ветки планов» показывает каждый участок отдельно, а не
  общий счётчик «40 из 200».
- **Не сдано в ОТК.** `C.0.07.04`: задача с истёкшим сроком и без отчёта — это
  разрыв, а не работа ОТК. Балансировка видит список и поднимает сигналы
  направлениям (защита от спама — 24 часа на направление).
- **Поток при приёмке.** Начисление перенесено в `acceptTaskService`
  (`C.0.07.02`): раньше Поток начислял только ОТК-сервис, и приёмка через
  `/tasks/:id/accept` оставляла исполнителя без начисления.
- **Отклонения и сигнал балансировки.** `C.0.06.03`: для каждого активного
  плана считается `overdue` (истёкшие сроки), `expectedDone` (сколько должно
  быть принято по времени до последнего чекпоинта), `breached`-чекпоинты и
  статус `behind / on_track / ahead`. Балансировка видит список отстающих
  планов на своей панели и **поднимает сигнал направлению** одной кнопкой
  (повторный сигнал по тому же плану — не чаще раза в 24 часа). Сигнал
  поднимается в двух случаях: **отстаёт** (просрочки/чекпоинты) и **идёт
  быстрее графика** — во втором текст просит перенести опыт на отстающие
  участки. Это ровно та роль балансировки, о которой вы говорили: заметить и
  позвать проверить, а не решать за направление.

- **Сигнал ↔ план.** `plans.signal_id` (D.2.01.36): из сигнала виден план и его
  прогресс, обратно — `GET /plans?signal_id=`. В интерфейсе сигнала появился
  блок «План по сигналу» с кнопкой «Создать план» и прогрессом по задачам.
- **Куратор плана.** `plans.curator_id` — конкретный человек; при создании плана
  он получает уведомление «Вы куратор плана», автор сигнала — «По вашему сигналу
  создан план».
- **Прогресс плана.** `getPlanProgress` считает задачи по обоим путям
  (`tasks.plan_id` и `plan_tasks`) и отдаётся прямо в ответе сигнала.

### 2.2 Чего ещё не хватает

1. **Ежедневный план как наряд.** `daily_plans` есть, но участник не видит
   «мой наряд на день» отдельным экраном — только список задач.
2. **Ноология.** По уточнению: ноология **всегда задаёт вопросы, если они есть**
   (например, проверяет планы). Сейчас это уведомление о заявке и плановая
   работа вне системы; нужен явный чек-лист вопросов к плану.

### 2.2 Что уже работает и не требует переделки

- Сигнал с обоснованием, приоритетом и направлениями; лимит итераций и эскалация.
- Ответы направлений на сигнал (support/clarify/reject) с обоснованием.
- План с критериями, чекпоинтами, стоп-условиями и подписью Хранителя.
- Декомпозиция задач через `parent_task_id` и привязка к плану.
- Сдача с артефактом (PR/коммит) и приёмка ОТК с начислением Потока.
- Уведомления по сигналам, задачам, ОТК и апелляциям с переходом к событию.

## 3. Слабые места: сводка

| # | Слабое место | Чем грозит | Как лечить |
|---|---|---|---|
| 1 | Нет ролей **наставник / координатор** как сущностей | наставничество живёт в реестре, но роль в правах не выдаётся | добавить `MENTOR`, `COORDINATOR` в `seedRoles` и матрицу прав |
| 2 | Заявка не несёт ответов на вопросы инкубации | ноологии нечего проверять | анкета в `registration_requests` (JSONB) + шаблон вопросов |
| 3 | Нет связи сигнал ↔ план | решение «повисает», прогресс не виден | `plans.signal_id` + экран «сигнал → план → задачи» |
| 4 | Нет куратора плана | некому отвечать за отклонения | `plans.curator_id` + уведомление |
| 5 | Нет расчёта отклонений | «дом отстаёт» узнают поздно | расчёт план/факт по чекпоинтам + автосигнал |
| 6 | Нет агрегации по родительской задаче | «20 домов» не видно как 20 веток | прогресс по `parent_task_id` в панели |
| 7 | Нет автоканала с наставником | общение вне системы | создавать `chat_channel` при назначении |
| 8 | Наставнику не начисляется Поток за ученика | наставничество — чистая нагрузка | правило начисления при приёмке работы ученика |
| 9 | Координатор не уведомляется | этапы провисают | роль + уведомления на переходы |

## 4. Порядок работ (предложение)

1. **Связь сигнал → план** и куратор плана — без этого «стройка» не читается.
2. **Роли `MENTOR` и `COORDINATOR`** + матрица прав и уведомления.
3. **Анкета инкубации** (вопросы в заявке) → ноология проверяет по факту.
4. **Отклонения по чекпоинтам** и агрегация прогресса по родительским задачам.
5. **Чат с наставником** и **Поток наставнику** — механика удержания опытных.

Пункты 1–2 дают «скелет», 3–5 — плоть. Начинать стоит с 1: он дешевле всего и
сразу делает путь сигнала наблюдаемым.
