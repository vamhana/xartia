## 0. Для чего существует этот документ

Этот документ — главный план реализации принятых правил XartIA в коде.

Он должен отвечать на практические вопросы:

1. Как именно система должна работать после реализации.
2. Что из этого уже есть в коде и в каком качестве.
3. Какие существующие компоненты и ID требуется изменить.
4. Какие новые компоненты, сущности, таблицы, API, интерфейсы и тесты требуется добавить.
5. В какой последовательности выполнять изменения и от чего зависит каждая фаза.
6. По каким сценариям и проверкам считать фазу завершённой.
7. Какие прежние механизмы после перехода должны быть удалены, отключены или оставлены для обратной совместимости.

Документ развивается версиями. Новые решения, результаты проверки кода и уточнения требований вносятся сюда. Он постепенно заменяет разрозненные TASK-F01 как источник заданий на реализацию.

**Главный результат:** код должен соответствовать принятым правилам и межфазовым контрактам XAD-01–XAD-20, закреплённым в v0.6. Кодовые изменения этой редакцией не подтверждаются. Синхронизация остальных документов выполняется после фиксации правил и целевой реализации в этом плане.

## 1. Источники истины и порядок разрешения противоречий

### 1.1. Целевая логика

Целевое поведение системы задают решения, принятые владельцем проекта в ходе обсуждений. При конфликте старой формулировки Хартии, TASK-файла или прежнего технического решения с более поздним принятым решением в план вносится принятое решение, а расхождение помечается для последующей синхронизации документации.

### 1.2. Текущее состояние системы

Для определения фактического состояния используются:

- `id_2.md` — актуальный реестр компонентов проекта, их ID, путей, зависимостей, API, миграций, тестов, ограничений и отмеченной реализации;
- `проект_клей_файл.md` — текущий кодовый слепок, по которому проверяется фактическое устройство функций, сущностей, SQL и API;
- рабочие книги и каталоги проекта, если конкретная фаза зависит от их структуры и содержания.

`id_2.md` и кодовый слепок считаются актуальной исходной парой для этой работы. Различие дат в метаданных само по себе не является основанием отвергать их актуальность.

### 1.3. Роль Хартии и TASK-файлов

Хартия и TASK-F01 используются как источники контекста, терминов, ранее зафиксированных требований и обнаруженных противоречий. Они не должны создавать параллельную, конкурирующую с этим планом инструкцию по реализации.

После переноса и сверки нужного содержания старые TASK-F01 получают один из статусов:

- `superseded` — заменён этим планом;
- `reference` — сохраняется как вспомогательный источник, но не задаёт реализацию;
- `retired` — более не используется;
- `active-reference` — временно нужен, пока соответствующая часть решений не перенесена полностью.

Никакие локальные файлы пользователя не удаляются. Речь только о статусе документации и её роли в процессе разработки.

## 2. Правила ведения плана и работы с ID

### 2.1. Существующие ID

Если существующий компонент сохраняет свою основную ответственность, его ID сохраняется. Изменение поведения функции, API или структуры таблицы само по себе не требует нового ID.

Новый ID создаётся, когда появляется самостоятельная архитектурная единица: отдельный сервис, контроллер, сущность/миграция, интерфейс, тестовый контур или документ, который имеет собственную ответственность и зависимости.

### 2.2. Новые ID

Перед резервированием нового ID необходимо проверить:

1. реестр `id_2.md`;
2. пути и заголовки компонентов кодового слепка;
3. существующие ссылки и зависимости;
4. отсутствие занятого, зарезервированного или устаревшего ID.

Не использовать пропущенный номер только потому, что он выглядит свободным: сначала проверить, не был ли он зарезервирован или исключён намеренно.

### 2.3. Предварительная нумерация

На момент версии 0.1 проверено:

- `X.0.01.41` не встречается в `id_2.md` и кодовом слепке; ID предлагается закрепить за этим главным планом;
- последняя зарегистрированная миграция в `id_2.md` — `D.2.01.72`; `D.2.01.73` — следующий свободный слот на момент сверки, но пока **не закреплён** за конкретной фазой;
- в реестре и кодовом слепке не найдены кандидаты `C.0.41.05`, `C.0.41.06`, `C.1.16.01`, `C.1.17.01`, `A.1.04.02`, `F.4.02.100`, `I.9.04.80`, `I.9.09.44`.

**Исправление нумерации относительно v0.1:** в первой версии `D.2.01.73` был предварительно поставлен на фазу 2 (смены), хотя фаза 1 (XSK/crosswalk) идёт раньше и тоже может потребовать миграцию. Это конфликт последовательности. В v0.2 `D.2.01.73` остаётся первым свободным слотом без жёсткой привязки. Если утверждённая модель XSK/crosswalk требует таблиц, этот слот сначала используется фазой 1; тогда миграции фаз 2 и далее получают последующие номера (`D.2.01.74+`). Все перечисленные новые ID — кандидаты, а не окончательно назначенные ID. Перед закреплением требуется повторный поиск по реестру и фактическим путям проекта.

## 3. Общая целевая архитектура

Система строится вокруг следующих связанных, но не тождественных сущностей:

1. **Направление** — профессиональная и организационная зона ответственности.
2. **Задача** — требуемый результат и причина, по которой он нужен.
3. **План реализации** — способ достижения результата, ресурсы, зависимости и критерии.
4. **Ячейка** — организационная структура/узел, внутри которого координируется работа.
5. **Смена** — конкретный рабочий интервал ячейки; в одной ячейке допускается до четырёх смен в сутки.
6. **Ростер смены** — временный состав конкретной смены, а не постоянное членство людей в ячейке.
7. **Мандат координатора** — ограниченная по времени ответственность за координацию; мандат не является привилегией и не тождественен одной смене.
8. **Общий наряд ячеек** — согласованный объём работы для соответствующих ячеек и уровней координации.
9. **Личный дневной план участника** — конкретная работа человека, подтверждаемая им до начала исполнения.
10. **ОТК** — проверка результата предыдущей смены по утверждённым критериям человеком, имеющим необходимые предметные и проверочные компетенции и не находящимся в конфликте интересов.
11. **Профессиональный паспорт** — подтверждённая индивидуальная проекция компетенций, доказательств, допусков и истории.
12. **TeamCapability** — способность конкретной конфигурации команды выполнить конкретную работу; её оценка относится к определённому составу и контексту, а не автоматически к любому будущему составу с тем же названием.
13. **События и версии** — неизменяемые свидетельства изменения состава, плана, ответственности, результата, оценки и состояния.

### 3.1. Принцип временного состава

Ячейка не должна пониматься как постоянная пятёрка с пожизненно закреплёнными участниками. Состав собирается под конкретную смену/работу и сохраняется в истории ростера.

Целевая базовая конфигурация — пять рабочих участников плюс координатор, всего шесть организационных позиций. Неполный состав допустим. Отсутствующие позиции фиксируются как дефицит покрытия, а не превращаются автоматически в ошибку или запрет на существование ячейки. Система должна показывать последствия дефицита и проверять, можно ли безопасно выполнять назначенную работу.

### 3.2. Принцип компетентности координатора

Не использовать жёсткую таблицу вида «L0 обязан знать профессию A, L1 — A+B, L2 — A+B+C».

Требования к координатору определяются динамически по атомам работ, входящих в фактическую зону ответственности, и по атомам координационной деятельности. Дополнительно проверяется связка атомов, необходимая для проведения ОТК. Один человек может координировать несколько ячеек, когда нет достаточного количества подходящих координаторов или имеются неполные ячейки, но только в пределах подтверждённой компетенции и реально покрываемой нагрузки.

L0/L1/L2 описывают масштаб покрытия ячеек/групп, а не универсальные профессиональные квалификации.

### 3.3. Принцип непрерывности

Задача не теряет идентичность при смене исполнителей, ростеров и координаторов.

Долгосрочная задача сохраняет постоянного институционального владельца — Совет направления, который принял решение о её запуске. Владение закрепляется за Советом как органом, а не за конкретным советником, текущим составом Совета или лицом, временно исполняющим его функции. Ротация состава Совета, координаторов и исполнителей не меняет владельца задачи.

Координатор отвечает за операционную непрерывность исполнения в пределах своей зоны/мандата: состояние текущей работы, организацию смены, передачу результатов, сигналов и незакрытых обязательств следующей смене.

Смена закрывается, результат и операционная ответственность передаются; сама задача продолжается, пока не изменена уполномоченным органом, не выполнена или не отменена по установленной процедуре.

Передача контекста или сигнала не считается завершённой передачей ответственности без подтверждения следующего получателя. Пока подтверждение не получено, операционная ответственность за передачу и незакрытые обязательства остаётся у передающего координатора, а сигнал эскалируется по резервному маршруту. Это не означает изменения или передачи постоянного владельца долгосрочной задачи.

### 3.4. Историческая модель

Использовать гибридную модель:

- в основных таблицах хранить актуальное состояние, необходимое для оперативной работы;
- в специализированных append-only журналах хранить значимые события;
- для планов, ростеров, конфигураций команды и передач сохранять версионные снимки;
- не переписывать историю задним числом;
- не переводить весь проект на полный Event Sourcing без доказанной необходимости.

## 4. Реестр принятых правил — целевое поведение

Ниже кратко сведены правила, которые должны быть отражены в фазах реализации. При детализации каждого правила добавляются: сценарии, исключения, акторы, проверки прав, события, ошибки, тесты и критерии приёмки.

### 4.1. Координатор и полномочия

| DEC | Целевое правило |
|---|---|
| DEC-01 | Система подбирает/назначает координатора на основе подтверждённых компетенций профессионального паспорта. |
| DEC-02 | Недельный мандат — ответственность, а не привилегия; он не тождественен конкретной смене или одному назначению. |
| DEC-03 | Окончательный ростер подтверждает координатор. Если он не утверждён до начала смены, система создаёт сигнал по цепочке для выяснения причины и возможного пересмотра задачи, плана или назначения координатора. |
| DEC-04 | Общий наряд ячеек подтверждают принимающие координаторы соответствующих ячеек; личный план подтверждает конкретный участник до начала работы. |
| DEC-05 | Личный план строится по стандартам, утверждённым Советом направления и подтверждённым компетентными затронутыми направлениями. Участник может направить сигнал наверх при обнаружении противоречия. |
| DEC-06 | Координатор контролирует готовность; система проверяет формальные условия; начало смены происходит по установленному времени, если нет основания для остановки/отмены. |
| DEC-07 | Координатор может изменить состав ячейки при наличии свободных подходящих участников, обязательно записав аргументацию. Изменения задачи/плана требуют повторного подтверждения затронутой смены. |
| DEC-08 | Координатор, принимающий и сопровождающий сигналы, решает вопрос самостоятельно в пределах своей компетенции и полномочий; при невозможности — эскалирует. Это та же координационная функция, а не отдельная должность. |
| DEC-09 | L0/L1/L2 различаются масштабом покрытия ячеек и групп; каждый отвечает за собственную зону. Это не статическая матрица предметных профессий. |
| DEC-10 | Приостанавливать работу и разрешать её возобновление могут Совет, координатор, Первый Архитектор и система в предусмотренных чрезвычайных случаях. Нужен отдельный прозрачный маршрут решения, фиксации основания и разрешения на возобновление. |

Рабочая панель — инструмент, а не второй план. |

### 4.3. Сигналы и передача ответственности

| DEC | Целевое правило |
|---|---|
| DEC-19 | Если следующий координатор не подтвердил передачу, ответственность остаётся у передающего координатора; отсутствие подтверждённого решения приводит к эскалации. |
| DEC-20 | Резервный получатель включается по тому же маршруту, когда следующий получатель не принимает ответственность в установленный срок/порядок. |

| DEC-22 | Непрерывность передачи сигналов между уровнями контролируется и совершенствуется когнитивными логистами; цифровая система должна предоставлять трассу маршрута, задержек и подтверждений. |

### 4.4. Долгосрочные задачи и ОТК

| DEC | Целевое правило |
|---|---|
| DEC-23 | За операционную непрерывность исполнения долгосрочной задачи между сменами отвечает координатор в рамках своей зоны/мандата. Он отвечает за состояние текущих работ, открытые обязательства, сигналы и подтверждённую передачу следующей смене. Эта ответственность не делает координатора владельцем долгосрочной задачи. Постоянный владелец определяется DEC-24. |

### 5.2. Уже обнаруженные разрывы, влияющие на фазы

1. Код считает базовую ячейку через `getSize` как пять участников всего; координатор помещается внутрь лимита. Целевая модель требует пять рабочих участников плюс координатор — шесть позиций.
2. `cell_daily_plans` организованы по паре `cell_id + date`; несколько отдельных смен одной ячейки в один день не выражены как отдельные сущности.
3. `getCellReadiness` требует полный состав, координатора, отдельного ОТК и общий план. Это не совпадает с допустимостью неполного ростера и новой моделью ОТК через компетентного координатора принимающей смены.
4. `CellMember` хранит интервалы членства, но версии наряда не сохраняют полный снимок состава ростера на смену.
5. `isCellCoordinator` проверяет только активную строку роли; система не проверяет предметные атомы, атомы координации, атомы ОТК, практику за последние шесть месяцев, недельный мандат и ограничение повторного назначения.
6. Личный план реализован как self-service `/learning/day-plans/me`; координатор не имеет полного процесса подготовки и публикации планов пяти участников будущей смены.
7. `TeamCapability.updateTeam` позволяет менять состав и критерии существующей сущности, при этом прежние оценки остаются связанными с тем же `team_id`; оценка может ошибочно восприниматься как относящаяся к изменившейся конфигурации.
8. ОТК проверяет исполнителя на самопроверку и связь с учителем по практике, но решение ОТК не связано с идентичностью предыдущей смены и автоматическим изменением паспорта по проваленному атому.
9. В коде есть проверка результата задачи и начисление Потока при принятии задачи, но нет полного правила «провал атома в конкретный день — Поток за этот день не начисляется».
10. Отдельные сущности историчны, но нет сквозной цепочки смена → ростер → личные планы → отчёт → ОТК → передача → подтверждение нового ответственного.
11. Каталог XSK существует отдельно от атомного каталога. Связи XSK-направление и XSK-атом не должны считаться готовыми только по наличию названий или классификационных областей.

### 5.6. Последовательность изменений и блокирующие зависимости

1. **Фаза 1 (XSK/crosswalk и CoordinatorProfile foundations)** должна определить, какие связи и версии компетенций используются при выдаче мандата. Нельзя до этого включать автоматический подбор координатора по неподтверждённым XSK-сопоставлениям.
2. **Фаза 2 (shift/roster)** должна предшествовать фазам подтверждений, отчётов и handover: личный план должен быть адресован конкретной смене, а не только календарному дню; OTK должен знать, какую предыдущую смену он принимает.
3. **Фаза 3 (мандат)** зависит от результата фазы 1 и модели временной зоны/покрытия фазы 2; generic mandates остаются базовым механизмом.
4. **Фаза 4 (наряд/личные планы)** зависит от shift ID и версий roster. Coordinator-authored draft и participant confirmation разделяются по правам.
5. **Фаза 5 (readiness/state machine/report)** зависит от подтверждений фазы 4 и модели дефицита roster фазы 2.
6. **Фаза 6 (handover)** зависит от shift lifecycle, отчетности, версии личных планов и signal routing.
7. **Фаза 7 (OTK/passport/Potok)** зависит от предыдущей смены, её отчёта, набора атомов assessor и handover. Day-level Potok нельзя определять только по одиночному `task_flow_awards`.
8. **Фаза 8 (task revision/Сouncil)** использует версии задачи/плана и сигналы; изменения должны направлять повторные подтверждения в затронутые смены.
9. **Фаза 9 (TeamCapability)** должна использовать те же идентификаторы временных конфигураций команды/смены, чтобы оценка не отрывалась от реального состава.
10. **Фаза 10 (сведение)** проверяет не только happy-path, но и повторы запросов, гонки, отмену, частичные сбои, миграцию существующих записей и обратную совместимость.

## 6. XSK и атомный каталог — входные ограничения для проектирования

Книга `XartIA_Skill_Catalog.xlsx` содержит в текущей версии:

- 322 XSK-навыка;

4. Соответствие должно иметь тип, статус, версию, основание, область действия и источник решения.
5. Координаторские профили должны ссылаться на подтверждённые атомы и/или на одобренные профили XSK с прозрачной трассировкой соответствий.
6. До завершения предметного сопоставления неподтверждённые связи не могут давать автоматический допуск.

### 6.2. Версионирование XSK и crosswalk

Книга имеет глобальную версию `v0.9.1`, а XSK-ID стабильны (`XSK-000001`–`XSK-000322`). В текущем листе `Навыки` нет полноценного отдельного поля версии для каждой записи. При этом шаблон карточки навыка предусматривает версию и дату вступления в силу. Поэтому ссылаться в паспорте или crosswalk только на голый `XSK-ID` недостаточно.

Требования к модели:

1. Каждая загруженная ревизия каталога должна иметь неизменяемую идентичность: release/version, источник, timestamp, checksum/снимок.
2. Каждая версия skill record должна быть адресуемой: либо явный `skill_version`, либо неизменяемый snapshot/hash плюс ссылка на релиз и исходный диапазон.
3. Crosswalk связывает конкретные версии XSK Skill и CYB.ATOM/его версии, а не только строковые ID.
4. Crosswalk должен быть many-to-many, версионированным и иметь состояние review/approval, основание, автора/инициатора, решение компетентного органа, область применимости и дату действия.
5. Изменение XSK-описания/критериев или атома не должно переписывать смысл старой связи; оно создаёт новую версию или требует повторной оценки связи.
6. Кандидатные типы связи (`exact`, `broader`, `narrower`, `partial`, `related`) — предложения для проектирования, а не принятый закрытый перечень. Их точный набор и семантика утверждаются до закрепления API/DB enum.
7. Неутверждённый crosswalk не используется для автоматического допуска, Matching или назначения координатора.

### 6.4. Профиль допуска координатора

`CoordinatorCapabilityProfile` строится под конкретную зону и конкретный состав ответственности. Минимальный концептуальный набор:

1. предметные атомы для работ, которые входят в зону;
2. атомы координационной деятельности, необходимые для планирования/сборки состава/сопровождения/эскалации;
3. атомы ОТК, необходимые для оценки результата и независимости проверки;
4. актуальные подтверждённые оценки по требуемым измерениям и критериям;
5. freshness/calibration state;
6. отдельные Permit, если конкретная работа их требует;
7. организационный мандат и scope как отдельный слой полномочий.

L0/L1/L2 характеризуют масштаб покрытия, а не подменяют этот профиль. Недельная ротация проверяющего — организационный порядок, не квалификация. Один и тот же человек может пройти проверку для одной зоны и не пройти для другой.

Текущий набор `CYB.ATOM.0001–0055` — инженерно-программный пилот, а не полный каталог координационных и ОТК-компетенций. В нём есть отдельные частично смежные атомы (требования, условия, декомпозиция, сравнение вариантов и педагогическая коммуникация), но не подтверждено полное покрытие сборки ростера, графика, назначения ресурсов/людей, подготовки личных планов, межъячеечного делегирования, маршрутизации сигналов, передачи ответственности и ОТК. Новые атомы не придумывать в техническом плане вместо предметного Совета/Коннекта: сначала пробел фиксируется как `missing_atom_requirement`, затем проходит установленную процедуру создания/утверждения.

До утверждения нужного набора атомов, критериев, применимости и crosswalk автоматический выбор координатора по DEC-01 не включается. Возможен только явно помеченный ручной/пилотный процесс, если он отдельно утверждён и не создаёт видимость автоматической квалификации.

### 6.5. Наставничество, риск и отдельные разрешения

Педагогическую пригодность нельзя вывести только из предметной компетенции. В текущем коде `TeachingRelation` использует proxy-пороги `P>=7`, `X>=5`, `E>=5`; педагогический атом `CYB.ATOM.0055` остаётся candidate, а XSK-000041–049 с минимумом 3 не утверждены. Дополнительно открыт междоменный вопрос CH-ZPO-04 (D11↔D14). Эти величины не применять как обязательное правило до решения Коннекта и предметной калибровки.

Точно так же G0–G5, уровень навыка 0–9, Permit, мандат координатора и TeamCapability должны оставаться разными типами результата. Нельзя автоматически переводить один тип в другой.

### Фаза 1. XSK, атомы, калибровка и безопасность паспортного допуска

**Цель:** создать достоверный, версионированный и безопасный слой компетенций; исключить возможность, чтобы черновой атом, неподтверждённая применимость или неутверждённый crosswalk давали автоматический Matching/допуск.

Она должна дать архитектуру, процедуру утверждения и безопасное поведение при неполных данных. Предметное утверждение выполняется уполномоченными Советами/Коннектом, а не разработчиком по сходству названий.

**Работы фазы 1:**

1. **Фиксация доменной модели.** Описать отдельно XSK Skill, CYB.ATOM, Direction, ZPO, relation/crosswalk, evaluation profile, level 0–9, gate G0–G5, Permit, mandate, TeamCapability и TeachingCapability. Для каждого типа определить источник истины, жизненный цикл и владельца утверждения.
2. **Импорт и версии XSK.** Зафиксировать источник workbook v0.9.1 как неизменяемый снимок. Определить хранение (read-only DB projection или versioned external artifact) и точную адресацию версии каждой skill record. Голый XSK-ID без версии/снимка не должен быть достаточным адресом в историческом crosswalk.
3. **Crosswalk.** Спроектировать версионированную many-to-many связь между конкретными версиями XSK и CYB.ATOM. Ввести review/approval state, основание, scope, источник, actor/authority и историю решений. Неутверждённая связь не участвует в автоматическом подборе.
4. **Направления/ЗПО.** Не выводить направление из названия навыка и не использовать маршрутную подсказку как решение. Все 322 XSK-связи с направлениями сейчас не сопоставлены; 13 открытых вопросов ЗПО остаются открытыми. Утверждение межнаправленных границ проводится отдельно.
5. **Applicability.** Заменить двоичную неоднозначность `applicable` на явное различение утверждённой применимости, утверждённой неприменимости и нерассмотренного состояния (или эквивалентную типизированную схему). `undetermined` должно возвращаться как `needs_review`, а не исчезать из требований; `not_applicable` требует причины/решения.
6. **Гейт статусов атома и критериев.** Оценка, способная стать `active/confirmed`, должна опираться на утверждённый атом и утверждённые критерии для соответствующего измерения. Matching и будущий CoordinatorProfile используют один общий guard. Кандидатные/черновые материалы могут существовать в каталоге и пилотном контуре, но не создают production eligibility.
7. **Переход пилотных данных.** Сейчас все 54 seed-атома (`CYB.ATOM.0001–0054`) отмечены как candidate/draft, а `CYB.ATOM.0055` тоже candidate. Нельзя просто включить approved-only фильтр без плана совместимости: определить, какой контур считается пилотным, какие записи будут утверждаться, какие операции временно останутся только ручными, и как не допустить выдачи реального допуска на неутверждённых данных. Пилотный bypass, если он нужен, должен быть явным, ограниченным и отдельно помечать результат как non-production.
8. **Коды причин Matching.** Различать отсутствие оценки, уровень ниже минимума, применимость не рассмотрена, атом/критерии не утверждены, оценка устарела/не откалибрована, Permit отсутствует/истёк. Не сводить всё к общему `missing` или `no_match`.
9. **Калибровка и свежесть.** Определить доменную схему anchor/assignment/outcome; незавершённую калибровку обозначать явно; корректно считать календарные периоды (например, P12M не подменять 360 днями). Калибровка является условием утверждения/использования только там, где это предусмотрено утверждённым процессом.
10. **CoordinatorCapabilityProfile foundation.** Спроектировать композицию предметных атомов зоны + координационных атомов + ОТК-набора. Вывести зависимости на смену/задачу/зону в виде требования, но само автоматическое назначение включать только после фаз 2–3 и закрытия предметных пробелов каталога.
11. **Техническая гигиена затронутых файлов.** При изменении модуля закрывать безопасные локальные долги из §5.7: стабильную сортировку истории, валидацию payload, единый helper ролей, согласованную сериализацию дат, пагинацию. Не расширять права и не менять бизнес-поведение «попутно» без отдельного требования.
12. **Реестр и документы.** Уточнить `id_2.md` по измерениям TaskProfile (`U/X/D/P/E`, не `D/I/P/E/U/X`), исправить ссылку миграции в записи `I.9.04.77` после проверки теста. Реестр XSK должен хранить фактические статусы, а не предполагаемые соответствия.

**Как должно работать после фазы 1:**

- XSK каталог можно читать с указанием точной версии, но его импорт не меняет паспорт и не присваивает направления;
- crosswalk хранит связь и историю, но автоматический Matching принимает только утверждённые связи;
- нерассмотренная применимость не трактуется как `false` или как `true` — возвращается явный review/blocker state;
- черновой atom или draft criteria не могут создать активное подтверждение и не могут удовлетворить обязательный профиль;
- результат Matching показывает точную причину, что отсутствует или не утверждено;
- level 0–9, G0–G5, Permit и mandate остаются разными сущностями;
- координаторский профиль может быть собран для конкретной зоны, но автоматическое назначение остаётся выключенным, пока набор атомов и правила назначения не готовы.

**Критерии приёмки фазы 1:**

1. Ни один из 322 XSK не получает направление, атом или статус утверждения по одному названию/автоматической эвристике.
2. Каждая используемая crosswalk-связь указывает конкретные версии XSK/ATOM, статус, основание, scope и орган/процедуру утверждения; candidate/rejected/expired link не даёт допуска.
3. Не рассмотренная applicability даёт `needs_review`; явно не применимое измерение требует основания; валидатор отклоняет malformed JSON и неизвестные состояния.
4. Попытка submit assessment для candidate atom или draft criteria завершается контролируемым отказом и не создаёт `active` assessment/`confirmed` person state.
5. Matching не использует candidate/draft атомы и критерии; различает минимум причины `not_assessed`, `below_minimum`, `applicability_undetermined`, `atom_not_approved`, `criteria_not_approved`, `stale_or_unverified`.
6. Календарный срок `P12M` обрабатывается как календарный период; состояние `calibration_pending/unknown` не считается автоматически свежим.
7. Пилотные записи не обходят production guard неявно; сценарий пилота явно помечен и проверен.
8. Затронутые паспортные smoke-тесты, включая `I.9.09.15` при изменениях calibration/freshness, проходят в проверенной рабочей ветке; результат подтверждён фактическим запуском, а не только просмотром кода.
9. Документация и реестр ID больше не расходятся по количеству измерений и миграционным ссылкам.
10. Ни один тест не утверждает педагогические пороги XSK-41–49/ATOM-0055 как обязательные до решения D11↔D14.

**Набор новых/расширяемых тестов:**

- candidate atom + draft criteria → submitAssessment отклонён, active/confirmed записи отсутствуют;
- approved atom + approved criteria + reviewed applicability → нормальная оценка проходит;
- applicability unknown → Matching возвращает needs_review, а не silently not_applicable;
- not_applicable без причины/решения → валидация не проходит;
- crosswalk 1:N и N:1 версионируется, но неподтверждённая связь не влияет на результат;
- изменение версии skill/atom оставляет прошлое решение читаемым и не переписывает историю;
- направление не выводится из имени XSK/области/предлагаемого маршрута;
- candidate atom не может удовлетворять профиль координатора;
- freshness: leap year/calendar P12M, неизвестная калибровка, истёкшее подтверждение;
- G0–G5, Permit, уровень 0–9 и мандат не могут подменять друг друга;

**Миграции:** `D.2.01.73` остаётся кандидатом. Сначала решить, где живёт авторитетный XSK каталог, какой shape applicability/crosswalk утверждён и нужен ли хранить его в БД. Если migration создаётся, предусмотреть backfill всех существующих записей в состояние, которое честно отражает факт непроверенности; не превращать прежние `applicable=true` в утверждённые без доказательства/решения. Никакие записи нельзя «одобрить» только ради успешной миграции.

**Технический долг, закрываемый в фазе 1:** P0 по applicability/status gating; P1 по калибровке, freshness, типизации payload и Matching gap codes; малые code-only исправления из пакетов A/B §5.7 — только в той мере, в которой затрагиваемые файлы уже изменяются и тесты можно запустить.

**Что не закрывается в фазе 1:** педагогические критерии наставника и `C.0.45.01`; lifecycle Permit, если нет непосредственного блокера; независимость повторного assessor; TeamCapability version binding; графовая производительность; полная предметная матрица координаторских атомов. Они сохраняются в фазах/реестре техдолга.

**Результат:** version-aware XSK model/crosswalk design, безопасные статусы атомов/критериев/applicability, корректный Matching, калибровка/freshness contract, базовая сборка профиля координатора и закрытые P0-проверки. Фаза 1 не считается выполненной, если в коде только создана таблица crosswalk, но кандидатные данные по-прежнему могут давать production eligibility.

- личный план опирается на стандарты Совета направления и подтверждённые межнаправленческие условия;
- участник не обязан молча соглашаться с противоречием: он отправляет сигнал по цепочке;
- изменение задачи или плана после подтверждения требует повторного подтверждения затронутых участников/смен;
- часы координации и собственная производственная работа координатора не учитываются дважды.

**Критерии приёмки:** план невозможно считать подтверждённым только фактом публикации; изменение ключевого содержания создаёт новую версию и снимает/обновляет прежние подтверждения; начало смены использует актуальные подтверждённые версии; план координатора остаётся единым планом его ответственности.

### Фаза 5. Готовность, старт, завершение и отчётность смены

**Цель:** реализовать полный автомат состояний смены и агрегирование отчёта вверх по иерархии.

**Изменяемые существующие ID:**
- `C.0.04.12` — readiness;
- `C.0.41.05–06` — смена и ростер (после создания);
- `C.0.06.02`, `C.0.06.05`, `C.0.06.06` — план, дерево и надзор;
- `A.1.04.01` / новые shift routes;
- `F.4.02.35`, `F.4.02.99` — панели и отчёты.

**Функции-кандидаты:** `checkShiftReadiness`, `startShiftAtScheduledTime`, `cancelShift`, `pauseShift`, `resumeShift`, `closeShift`, `buildShiftReport`, `aggregateHierarchicalShiftReport`.

**Как должно работать:**
- координатор контролирует готовность;
- система проверяет формальные условия и показывает дефициты;
- старт происходит по расписанию, если смена не отменена/не остановлена;
- неполный состав допускается, но система проверяет пригодность конкретного плана к имеющемуся покрытию;
- отмена/остановка/возобновление имеют отдельные основания, полномочия и историю;
- итоговый отчёт содержит покрытие плана, факты, проблемы, сигналы, решения и обязательства;
- отчёты нижних ячеек собираются в отчёт группы/верхнего уровня.

**Критерии приёмки:** нет старта без актуального состояния и проверок; отмена после старта не стирает факт работы; отчёт восстанавливается по смене; агрегат верхнего уровня трассируется к дочерним сменам и их версиям.

### Фаза 6. Передача смены, сигналов и ответственности

**Цель:** обеспечить непрерывную передачу открытой работы и сигналов между координаторами и уровнями.

**Изменяемые существующие ID:**
- `C.0.10.02` — сигналы;
- `C.0.04.13` — сигналы перестановки;
- `C.0.41.05–06` — состояние смены, ростеры и handover;
- `C.0.07.02` — непрерывность задачи;
- `C.0.06.06` — дерево надзора;
- `A.1.04.21` и соответствующие сигналам API;
- `D.2.01.54`, `D.2.01.57` и новые миграции событий/передач.

**Кандидаты новых сущностей:** `shift_handover_packages`, `handover_acceptances`, `signal_responsibility_transfers`, `coordinator_coverage_assignments`.

**Функции-кандидаты:** `buildHandoverPackage`, `submitHandover`, `acceptHandover`, `transferSignalResponsibility`, `escalateUnacceptedHandover`, `resolveSignal`, `closeSignalByOriginator`.

**Как должно работать:**
- передаются состояние задачи, версии планов, фактические результаты, решения ОТК, замечания, сигналы, зависимости и незавершённые назначения;
- у каждого сигнала сохраняются исходный ID, отправитель, объект, версия плана, текущий статус, следующий шаг и следующий ответственный;
- передача ответственности считается завершённой после подтверждения следующего получателя;
- если подтверждения нет, ответственность остаётся у передающего координатора, затем включается резервный маршрут/эскалация;
- окончательное решение принимается по процедуре, соответствующей масштабу вопроса;
- отправитель закрывает сигнал после разрешения проблемы и подтверждения исполнения решения;
- когнитивные логисты получают данные для анализа задержек и улучшения маршрутов.

**Критерии приёмки:** сигнал не теряет ответственного при завершении смены; система воспроизводит всю цепочку передач; неподтверждённый handover автоматически эскалируется; одна долгосрочная задача продолжает жить через несколько смен без создания фиктивной новой задачи.

### Фаза 7. ОТК предыдущей смены, паспортные последствия и Поток

**Цель:** связать приёмку смены с профессиональными компетенциями, независимостью ОТК, изменением паспорта и начислением Потока.

**Изменяемые существующие ID:**

- `C.0.07.02` — жизненный цикл результата задачи;
- `C.0.14.01` — начисление Потока;
- `C.1.03.01–02`, `C.1.02.02` — оценки и история паспорта;
- `C.1.09.01–02` — связи наставничества и учебная практика;
- `D.2.01.49–52`, `D.2.01.58–65` — Поток, решения ОТК и паспорт.

**Функции-кандидаты:**
- `selectIncomingShiftAssessor`;
- `checkAssessorAtomEligibility`;
- `checkAssessorIndependence`;
- `assessPreviousShift`;
- `recordAtomFailure`;
- `updateParticipantAtomState`;
- `suspendIndependentAtomAccess`;
- `scheduleRetrainingAndReassessment`;
- `updateTeachingCapabilityForAtom`;
- `settleShiftFlowAfterOtk`.

**Как должно работать:**
- входящий координатор проверяет результаты предыдущей смены, а не собственную текущую работу;
- проверка атома разрешена только при подтверждённой компетенции оценщика по предмету и атомам ОТК;
- исключается самопроверка и проверка бывшего ученика по соответствующему атому;
- ОТК мандат/период ротации проверяется отдельно от квалификации; недопустимо постоянное закрепление одного человека в проверке;
- отрицательный результат создаёт событие с атомом, исполнителем, оценщиком, основанием, версией критерия и связанной оценкой;
- паспорт исполнителя обновляется по конкретному атому, самостоятельный допуск блокируется до переподготовки и повторной проверки;
- учителю может быть снижена педагогическая способность обучать этому атому, но не автоматически предметная оценка;
- оценка проверяющего может быть пересмотрена отдельной процедурой;
- день провала не приносит Поток; правило применяется на уровне всего дня, а не только одной проваленной задачи;
- успешная практика с начисленным Потоком может дать подтверждающее событие профпригодности, но сама по себе не повышает уровень 0–9.

**Критерии приёмки:** невозможно начислить Поток за день, где зафиксирован провал атома; повторный запрос не дублирует/не восстанавливает начисление; паспорт сохраняет причину и автора изменения; самостоятельный допуск не возвращается без новой проверки; педагогическая и предметная оценки не смешиваются.

### Фаза 8. Долгосрочные задачи, декомпозиция и пересмотр Советом

**Изменяемые существующие ID:**

- `C.0.41.*` — перестройка смен и ячеек;
- `D.2.01.67` и связанные миграции зависимостей/версий задач.

**Функции-кандидаты:**
- `reviseTaskByCouncil`;

- `rebuildImplementationPlan`;
- `decomposeTaskToComponents`;
- `approveRequirementAffectingDecomposition`;

**Как должно работать:**
- изменение цели/требований принадлежит Совету, а не личному решению координатора;
- план можно изменить, не изменяя задачу; изменение задачи может вызвать новый план и перестройку ячеек;
- завершение 9 из 10 компонентов отображает 90%, но не закрывает родительскую задачу;
- координатор разбирает незавершённый компонент и эскалирует нерешаемое;
- родительская задача закрывается только положительным ОТК;
- при отсутствии компетентных исполнителей система направляет сигнал Совету;
- межнаправленческие зависимости фиксируются на этапе постановки задачи и затем сохраняются как связанные задачи/решения;
- постоянным владельцем долгосрочной задачи остаётся Совет направления, который принял решение о её запуске; связь с Советом-инициатором сохраняется независимо от ротации состава Совета, смены координаторов и исполнителей;
- `assignedTo` и `assignedBy` используются для назначения и исполнения конкретных работ/deliverables и не определяют владельца долгосрочной задачи;
- координатор отвечает за операционное сопровождение исполнения и передачу незакрытых обязательств следующей смене, не подменяя постоянного владельца.

**Критерии приёмки:** прогресс родителя вычисляется без ручной подмены; 90% не равняется `completed`; изменение требования сохраняет предыдущую версию и запускает маршрут пересмотра; отсутствие специалистов порождает сигнал Совету; история старой и новой организации ячеек восстанавливается; долгосрочная задача сохраняет постоянную связь с Советом, который её запустил; ротация состава Совета, смена координатора или исполнителей не изменяет владельца; исполнительские назначения не подменяют институциональное владение.

**Цель:** привязать командную оценку к реальной конфигурации людей и задаче, не перенося старую оценку на изменившуюся команду.

**Изменяемые существующие ID:**

**Функции-кандидаты:** `createTeamConfigurationVersion`, `reviseTeamConfiguration`, `assessTeamConfiguration`, `getTeamConfigurationHistory`, `resolveApplicableTeamAssessment`.

**Как должно работать:**
- TeamCapability связан с идентификатором задачи/ожидаемого результата и точной версией состава;
- изменение состава, критериев или существенного результата создаёт новую версию;
- оценка фиксирует ссылку на конкретную версию и не переносится на новую автоматически;
- состав может быть временным и соответствовать одной смене или определённому рабочему периоду;

**Критерии приёмки:** после изменения состава система показывает, что прежняя оценка относится к прежней версии; нельзя получить текущий статус новой конфигурации из старой оценки; аудит позволяет восстановить конкретный состав и задачу на момент оценки.

## 9. Минимальный набор сквозных проверок

На всём протяжении реализации поддерживать единый сценарный набор:

1. Координатор выбран по атомам конкретной зоны, не прошёл — назначение отклонено.
2. Один человек получает недельный мандат; истечение, повторное назначение и cooldown соответствуют утверждённой политике. Месячный лимит не тестируется как обязательный, пока он не принят отдельно.
3. Одна ячейка имеет четыре смены за сутки с независимыми ростерами и отчётами.
4. Ростер неполный, но допустимый; система показывает дефицит и оценивает, какие задачи реально можно выполнять.
5. Ростер подтверждён координатором; общий наряд — принимающим координатором; личный план — участником.
6. Изменение задачи/плана после подтверждения требует повторного подтверждения затронутой смены.
7. Координатор покрывает несколько ячеек в разрешённых границах атомов и нагрузки.
8. Передача сигнала не подтверждена — ответственность остаётся у передающего, срабатывает эскалация.
9. Долгосрочная задача сохраняет постоянного институционального владельца — Совет направления, который запустил её. Смена координаторов, исполнителей, ростеров и ротация состава Совета не меняют владельца. Передача смены изменяет операционную ответственность, но не институциональное владение задачей.
10. ОТК проверяет предыдущую смену, не может проверить собственную работу или работу бывшего ученика по атому.
11. Провал атома обновляет паспорт, блокирует самостоятельный допуск, запускает переподготовку; Поток за день провала не начисляется.
12. Ошибка учителя по педагогической способности не понижает автоматически предметную компетенцию.
13. Девять из десяти дочерних задач дают 90%, но родительская задача не закрыта.
14. Положительный ОТК закрывает родительскую задачу.
15. Совет пересматривает задачу; новый план и новая организация ячеек сосуществуют с сохранённой историей прежнего цикла.
16. Изменение состава TeamCapability создаёт новую версию; старая оценка остаётся привязана к старому составу.
17. История позволяет восстановить, кто, когда и на каком основании изменил задачу, ростер, план, назначение, результат, ОТК, паспорт и ответственность.


**Дополнительные сквозные проверки для фазы 1 (обязательны до включения автоматического допуска):**

18. Candidate atom/draft criteria не создают active assessment и не закрывают обязательное требование Matching.
19. Applicability в состоянии unknown/undetermined не считается ни применимой, ни неприменимой: возвращается явный `needs_review`.
20. Reviewed `not_applicable` без причины/решения не может быть сохранено.
21. Утверждённая crosswalk связь адресует точные версии XSK и ATOM; изменение одной версии не меняет прошлую оценку связи.
22. Неутверждённая crosswalk-связь и route suggestion не участвуют в подборе направления, исполнителя или координатора.
23. Freshness P12M рассчитывается календарно, а отсутствие калибровки не считается свежей оценкой.
24. G0–G5, уровень 0–9, Permit, mandate и TeamCapability не могут взаимно подменяться при проверках допуска.
25. Пилотный режим, если сохранён, явно отделён от production eligibility и имеет отдельный отрицательный тест на утечку в production.

## 10. Политика перехода со старых TASK-F01

Старые TASK-F01 не удаляются и не переписываются массово заранее.

Переход выполняется так:

1. Решение и полезные детали извлекаются из TASK.
2. Содержание переносится в соответствующую фазу этого документа.
3. Оно сравнивается с принятыми DEC и текущим кодом.
4. После включения в основной план исходный TASK получает статус `superseded` или `reference`.
5. Если в TASK обнаружено решение, не включённое в DEC, оно не становится требованием к коду автоматически — требуется отдельное подтверждение.

Внешним ИИ для реализации передаётся этот план, нужные разделы `id_2.md`, точечные исходники и тесты. Передача полного старого набора TASK больше не является обязательной.


## 5.8. Уточнение P0: паспортный допуск — аудит цепочки и порядок исправления (v0.4)

### 5.8.1. Подтверждённая цепочка дефекта

Статическая сверка кодового слепка `проект_клей_файл.md` выявила не один локальный пропуск, а сквозной разрыв между статусом каталога и производным состоянием паспорта:

1. `I.9.09.01` (`scripts/seed-data/atoms.ts`) создаёт пилотные атомы со статусом `candidate`; helper `a()` по умолчанию задаёт `assessment_criteria.status = 'draft'`. Полные карточки 0001–0010 также имеют `status: 'candidate'` и `assessment_criteria.status: 'draft'`.
2. `C.1.03.01` (`src/core/passport/assessment.ts`) в `submitAssessment()` проверяет существование атома, применимость измерения и роль проверяющего, но не требует `atom.status === 'approved'` и `atom.assessment_criteria.status === 'approved'`.
3. Та же функция вставляет assessment со статусом `active` и обновляет `person_atom_states.status = 'confirmed'`. То есть черновая карточка может породить подтверждённое состояние участника.
4. `C.1.10.01` (`src/core/passport/matching.ts`) проверяет покрытие по `person_atom_states`: `confirmed` или `provisional` плюс уровень. В запросе атомов берётся только `atom_id` и `dimension_applicability`; статусы атома и критериев не загружаются и не проверяются.
5. `getCandidates()` реализует отдельный пакетный путь вычисления кандидатов. Он также должен использовать тот же доменный gate, иначе исправление только `matchTask()` оставит обходной путь.
6. `C.1.02.01` (`catalog.ts`) отображает статус каталога, но сам по себе не защищает путь оценки. `C.1.15.01` (`catalog-proposals.ts`) валидирует форму `dimension_applicability` недостаточно глубоко: сейчас проверяются тип объекта и допустимость ключей, но не полный контракт каждой записи.

**Вывод:** сейчас `candidate/draft` — не просто метки интерфейса. Из-за отсутствия серверного gate они не являются запретом на production assessment и Matching. Это P0, поскольку может приводить к ложному подтверждению профессиональной компетенции.

### 5.8.2. Отдельный дефект контракта применимости

В актуальной документации `id_2.md` для пилотного набора 0011–0054 задано `dimension_applicability = { U..E: { applicable: true, status: "pending_review" } }`. Фактический seed `I.9.09.01` задаёт для этих атомов только `applicable: true`, без `status`; интерфейс `DimensionApplicabilityEntry` в `C.1.01.01` также не содержит review-status. `isDimensionApplicable()` возвращает `true` только по boolean `applicable === true`.

Следствие: документация и реализация расходятся, а `applicable: true` фактически трактуется как окончательно разрешённая применимость, хотя в документации она находится на рассмотрении. Отсутствующая запись измерения, в свою очередь, трактуется как `false`, то есть может молча превратиться в `not_applicable`.

Это отдельный P0-контракт, который нельзя закрыть простой заменой `true` на `false`. Требуется трёхзначная семантика:
- `applicable` — измерение рассмотрено и признано применимым;
- `not_applicable` — рассмотрено и признано неприменимым, обязательно основание;
- `undetermined` — решение ещё не принято; это не эквивалент `not_applicable`.

Физическая форма хранения (boolean + review status либо явный enum) должна быть единообразной в типах, seed, API, БД-контракте и документации. Не вводить параллельные несовместимые варианты.

### 5.8.3. Предлагаемый доменный gate

До завершения фазы 1 ввести единый серверный доменный механизм, используемый `submitAssessment`, `matchTask`, `getCandidates` и будущим `CoordinatorProfile`.

Assessment допускается к `active` и `confirmed`, только если одновременно выполнены условия:

1. Атом существует и имеет статус `approved`.
2. Критерии оценки имеют статус `approved`.
3. Для конкретного измерения применимость явно рассмотрена и имеет итог `applicable`.
4. Версия атома и критериев фиксируется в assessment (существующий `criteria_version` уже хранит версию атома; нужно проверить, достаточно ли этого для независимой версии критериев).
5. Проверяющий имеет право оценивать соответствующее измерение и не оценивает собственную работу — существующие проверки сохраняются.

`candidate`, `draft`, `in_review`, `deprecated`, отсутствующий статус, неполный контракт критериев или `undetermined` applicability не могут создавать `active/confirmed`.

Предлагаемые машинно-различимые причины отказа:
- `atom_not_approved`;
- `criteria_not_approved`;
- `applicability_undetermined`;
- `dimension_not_applicable`;
- `assessment_criteria_invalid`.

Не следует маскировать эти причины общим `ATOM_NOT_FOUND` или `missing_dimensions`.

Для Matching:
- `approved` atom + `approved` criteria + reviewed applicability — допускаются к оценке покрытия;
- `candidate/draft/in_review/deprecated` — требование считается заблокированным, с критическим gap `atom_not_approved` либо `criteria_not_approved`;
- `undetermined` applicability — `applicability_undetermined`, никогда не пропускается как неприменимое измерение;
- `not_applicable` — измерение исключается из проверки только при наличии утверждённого основания;
- неизвестный atom ID в профиле — критический `atom_not_found`;
- отсутствие оценки и недостаточный уровень различаются как `not_assessed` и `below_minimum`.

`matchTask()` и `getCandidates()` обязаны вызывать один общий алгоритм оценки требований. Пакетная реализация кандидатов может оптимизировать чтение, но не может иметь собственную, более мягкую семантику допуска.

### 5.8.4. Безопасный переход существующих данных

До доступа к рабочей БД нельзя утверждать, сколько реальных `active` assessments и `confirmed` states уже существуют по candidate/draft атомам. Кодовый слепок подтверждает дефект пути записи, но не подтверждает фактический объём загрязнённых данных.

Порядок перехода:
1. Сделать read-only инвентаризацию пар `competency_atoms.status`, `assessment_criteria.status`, `passport_assessments.status`, `person_atom_states.status`.
2. Сохранить исторические assessments и события; ничего не удалять и не переписывать задним числом.
3. Для несовместимых оценок определить отдельный безопасный статус/флаг блокировки использования. Нельзя считать их автоматически отклонёнными: это исторические результаты, которые могли быть реальными, но получены на неутверждённых критериях.
4. Исключить такие оценки из production Matching до повторной проверки/калибровки.
5. Повторная оценка должна создавать новую запись и событие; прежняя запись сохраняется как исторический факт.
6. `person_atom_states` пересчитать из последнего допустимого assessment либо перевести в `calibration_pending/under_review` только по явно утверждённому правилу. Не обнулять уровни без сохранения причины и истории.

Миграция не должна автоматически переводить 54 candidate атома в `approved` и не должна «лечить» данные простым массовым UPDATE.

### 5.8.5. Тестовые фикстуры и регрессии

Найден дополнительный риск: текущие интеграционные тесты паспорта используют атомы из пилотного каталога (например, `CYB.ATOM.0030–0034`) для успешного создания assessments. После введения корректного gate эти тесты закономерно начнут получать отказ, поскольку seed объявляет такие атомы candidate/draft.

Требуемое изменение тестового контура:
- завести отдельные тестовые атомы/фикстуры с явно утверждённым атомом, утверждёнными критериями и утверждённой применимостью;
- не менять production seed на approved ради прохождения тестов;
- отдельными негативными сценариями использовать candidate atom, draft criteria и undetermined applicability;
- проверить, что после отказа не появились `passport_assessments(active)`, `person_atom_states(confirmed)` и `assessment_activated` event;
- один и тот же набор кейсов прогнать через `matchTask()` и `getCandidates()`, чтобы исключить расхождение;
- проверить, что approved atom с draft criteria также блокируется;
- проверить, что not_applicable с пустым reason не проходит валидацию.

### 5.8.8. Критерии закрытия P0

P0 считается закрытым только если одновременно:
- candidate atom + draft criteria не создают active assessment и confirmed state;
- approved atom + draft criteria отклоняется;
- approved atom + approved criteria + applicability applicable проходит;
- undetermined applicability возвращает needs-review/gap и блокирует eligibility;
- not_applicable без основания не принимается;
- `matchTask()` и `getCandidates()` дают одинаковый смысловой результат;
- ни один отказ не создаёт историю `assessment_activated` и не меняет текущий state;
- все исторические записи сохранены и их production-использование определено отдельным безопасным переходом;
- тесты пройдены на актуальной ветке, а не только статически прочитаны.

### 13.3. Clarifications of boundaries

1. **Matching vs TeamCapability:** individual atom Matching decides whether each assigned person may perform their role. TeamCapability assesses demonstrated ability of the exact group to produce a result. Neither replaces the other.
2. **Mandate vs assignment:** CoordinatorMandate is temporary authority across an explicitly defined scope; CoordinatorAssignment allocates actual shift/coverage duty; roster membership is a separate production position.
3. **Shift close vs handover:** shift close records actual result/report; responsibility transfers only on item acceptance in Phase 6.
4. **TaskRevision vs PlanVersion vs ImplementationCycle:** TaskRevision changes objective/expected result/scope/mandatory quality criteria; PlanVersion versions the shared direction Plan; ImplementationCycle binds one TaskRevision to its execution tree inside that Plan.
5. **Parent progress vs parent completion:** mandatory child progress can be 100%; parent completes only after independent ParentOutcomeReview is positive.
6. **Task-level award vs participant-day settlement:** `task_flow_awards` protects one award per task only. It cannot alone enforce day-level no-Potok after atom failure.
7. **Team assessment vs passport event:** a team result is not an individual passport change and is not written as such.

### 13.4. Decisions that remain outside technical delegation

Quorum/voting/Connect/Jury, legal Permit scope, pedagogical criteria and D11↔D14, emergency authority, succession of a dissolved Council, and production release acceptance/restore authorization remain governed by existing charter/competent procedures. If no such rule exists for an action, keep that action blocked; do not invent it.
