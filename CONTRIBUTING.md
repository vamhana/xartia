# Как присоединиться к XartIA

Спасибо, что зашли. Здесь можно помочь, даже если вы не программист.
Ниже — все пути: от «задать вопрос» до «сделать первый PR».

**Правило первое:** непонятно — спрашивайте. За вопрос не наказывают.
**Правило второе:** здесь нет слабых и сильных. Есть люди с разным
уровнем знаний, и они им делятся.

---

## 1. Куда писать

| Что | Куда |
|---|---|
| Идея, сомнение в Хартии, спор о смысле | [GitHub Discussions](https://github.com/vamhana/xartia/discussions) |
| Быстрый вопрос, «а как это работает» | [Telegram: hartia_5](https://t.me/hartia_5) |
| Ошибка в коде/интерфейсе | [Issues](https://github.com/vamhana/xartia/issues/new/choose) |
| Первая задача | метка [`good first issue`](https://github.com/vamhana/xartia/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22) |
| Уязвимость/секрет в коде | **не публикуйте в issue** — напишите в Telegram лично |

Мы стараемся отвечать в течение суток (по возможности быстрее). Если
ответа нет — это не «вас игнорируют», а «человек занят»; напомните о себе.

## 2. Если вы не программист

Помочь можно так:

1. **Прочитать Хартию** и принести вопросы: <https://vamhana.github.io/hartia/charter/>.
2. **Проверить Хартию на прочность** через любой ИИ: где противоречия,
   где правило нельзя реализовать, где оно превращается в произвол.
3. **Написать сценарий** «как я вижу первый день хартийца» — что должно
   произойти, чтобы человек не ушёл.
4. **Найти непонятное место в документации** и сказать о нём. Это
   реальная работа: если вам непонятно — непонятно будет многим.

Для этого не нужно устанавливать проект. Достаточно Discussions/Telegram.

## 3. Если вы разработчик: первый запуск

Нужны: **Docker**, **Node.js 22+**, **pnpm**.

```powershell
git clone https://github.com/vamhana/xartia.git
cd xartia
pnpm install

docker compose -f docker/docker-compose.yml up -d postgres redis minio

pnpm db:migrate
pnpm tsx scripts/ensure-architect.ts   # создаст Архитектора из .env
pnpm db:migrate                        # сиды (роли, направления, панели)

pnpm dev                                # API :3000, WS :3001, web :5173
```

Проверки перед PR:

```powershell
pnpm typecheck        # типы API
pnpm typecheck:web    # типы веба
pnpm exec vitest run  # юнит-тесты (если есть)
pwsh scripts/ci-local.ps1  # полный прогон, как в CI (Windows)
```

Если что-то не поднялось, сначала загляните в
[docs/troubleshooting.md](docs/troubleshooting.md) (порты, Docker/WSL,
миграции, Архитектор, 401/404). Если не помогло, напишите в Telegram:
укажите шаг и текст ошибки. Скриншот приветствуется.

## 4. Карта кода

```
src/core/       — домен: задачи, ОТК, Поток, казна, Совет, ячейки, Шлюз
src/api/        — REST-контроллеры (Fastify)
src/ws/         — WebSocket-каналы
src/web/        — React-интерфейс (страницы, компоненты, панели)
db/migrations/  — схема БД (56 миграций)
scripts/        — smoke-тесты и обслуживание
docs/           — Хартия, продукт, карта «Хартия → код»
```

Куда смотреть в зависимости от задачи:

| Хочу… | Смотреть |
|---|---|
| понять правило приёма задачи | `src/core/tasks/service.ts` |
| разобраться с Потоком | `src/core/flows/` |
| казна, пол 1.00, 3/5 | `src/core/treasury/` |
| Совет и мандаты | `src/core/council/`, `src/core/mandates/` |
| ячейки, ёмкость, готовность | `src/core/cells/` |
| Шлюз | `src/core/gateway/` |
| интерфейс | `src/web/pages/` |
| схема данных | `db/migrations/` |

Карта «принцип Хартии → модуль → тест»:
[docs/charter-implementation-map.md](docs/charter-implementation-map.md).

## 5. Первый вклад: три дороги

### Дорога A — документация (30–60 минут)

- Исправить неточность в README/CONTRIBUTING.
- Дописать `docs/troubleshooting.md` по реальной ошибке, которую поймали.
- Перевести один раздел на английский (когда решим bilingual).

### Дорога B — тест (1–3 часа)

- Добавить проверку в существующий smoke-скрипт.
- Воспроизвести баг тестом, который сейчас падает.

### Дорога C — небольшой код (вечер)

- Взять `good first issue`, где указано: что сделать, где файл, как проверить.
- Не брать задачу, в которой не понимаете половину, — лучше спросить.

**Как взять задачу:** напишите в issue «беру» — мы закрепим её за вами.
Если передумали — тоже напишите, это нормально.

## 6. Как сделать PR

1. Форкните репозиторий.
2. Ветка: `feat/короткое-название` или `fix/короткое-название`.
3. Делайте маленькие коммиты; сообщение — в императиве:
   `fix(tasks): не принимать задачу без артефакта`.
4. Перед PR прогоните проверки из раздела 3.
5. В описании PR: **что** изменилось, **зачем**, **как проверить**.
6. Если PR меняет правило Хартии — приложите ссылку на обсуждение.

Ревью: один человек смотрит код, второй — смысл (если правило спорное).
Замечания — не «ты плохой», а «здесь можно иначе». Спорить можно,
обосновывать нужно.

---

## 7. Чего мы не делаем

- Не обесцениваем чужой уровень и не устраиваем «экзамен на входе».
- Не приватизируем роли: мандат истекает, его нельзя «оставить себе».
- Не смешиваем Поток (вклад) с деньгами и властью.
- Не принимаем работу без артефакта и проверки.
- Не молчим о проблемах: сигнал лучше, чем тишина.
