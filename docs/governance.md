# Governance: как менять ядро XartIA

Это правила **изменения правил**. Они сами могут быть изменены —
через предложение типа `meta`.

## 1. Что считается изменением ядра

| Тип | Что меняет | Пример |
|---|---|---|
| `module` | поведение функции | новая формула Потока, критерии ОТК |
| `rule` | правило системы | порог подписей казны, SLA проверки |
| `charter` | статью Хартии | формулировка «мандат не приватизируется» |
| `meta` | сам процесс обсуждения/решения | дедлайн, кворум, типы возражений |

**Breaking change** — изменение, которое ломает совместимость:
формулы, пороги, форматы API, обязательные поля, исторические данные.
Оно обязано быть помечено `breaking` и иметь план миграции.

## 2. Жизненный цикл предложения

```
draft → discussion (дедлайн) → agreed → implementing → accepted
                     ↘ rejected        ↘ withdrawn
```

| Статус | Кто переводит | Что означает |
|---|---|---|
| `draft` | автор | проблема и предложение сформулированы |
| `discussion` | автор / Совет / Архитектор | открыто обсуждение, идёт дедлайн |
| `agreed` | Совет / Архитектор | решение принято, можно реализовывать |
| `rejected` | Совет / Архитектор | отклонено с обоснованием |
| `implementing` | реализующий | есть PR |
| `accepted` | Совет / Архитектор | изменение влито и проверено |
| `withdrawn` | автор / Совет | отозвано |

## 3. Дедлайн и молчание

- По умолчанию обсуждение — **7 дней** (можно 1–30).
- Молчание **не равно согласию** для `breaking` и `charter`.
- Для обычных `module`-изменений: если за дедлайн нет открытых
  возражений — предложение можно выносить на решение.
- Просроченное обсуждение эскалируется Совету (в будущем — worker).

## 4. Возражения

| Тип | Смысл | Кто закрывает |
|---|---|---|
| `factual` | «в коде/данных не так» | автор — ссылкой на код/тест |
| `conceptual` | «противоречит Хартии/смыслу» | автор отвечает, Совет решает |
| `compatibility` | «сломает X, Y, Z» | обязателен план миграции |

Правила:
- возражение принимается только в статусе `discussion`;
- нельзя возражать самому себе;
- **нельзя принять предложение с открытыми возражениями** — сначала
  нужно ответить и закрыть (`addressed`/`rejected` с обоснованием);
- закрытие возражения — это запись, а не удаление.

## 5. Кто принимает решение

- **Совет направления** — для `module` и `rule`.
- **Архитектор** — при отсутствии Совета или для срочных случаев,
  с письменным обоснованием.
- **`charter` и `meta`** — повышенный барьер: решение Совета +
  Архитектор (в будущем — кворум 2/3). Пока фиксируется метод
  (`council`/`architect`/`consent`/`vote`) и обоснование.

Решение **не может быть принято без обоснования** (минимум 20 символов)
и без указания затронутых инвариантов (для `module`/`rule`).

## 6. Реализация

PR должен содержать:

1. ссылку на предложение (`Proposal: #id`);
2. список затронутых инвариантов и как они проверяются;
3. миграцию, если меняется схема;
4. тест, который падал бы без изменения;
5. обновление `docs/charter-implementation-map.md`, если смысл изменился.

Принятие (`accepted`) — только после зелёного CI и проверки, что
инварианты не нарушены.

## 7. Где это живёт в системе

| Объект | Где |
|---|---|
| Предложения | `proposals`, API `/proposals` |
| Возражения | `proposal_objections` |
| Решения | `proposal_decisions` |
| Влияние | `proposal_impacts` |
| Инварианты | `invariants`, API `/invariants` |
| История переходов | `proposal_events` |
| Обсуждение | GitHub Discussions + ссылка в предложении |

## 8. Как изменить сами эти правила

Создайте предложение типа `meta`:

```
POST /proposals
{
  "type": "meta",
  "title": "Сократить дедлайн обсуждения",
  "problem": "...",
  "proposal": "...",
  "invariants": ["audit_traceable"]
}
```

Дальше — тот же цикл: обсуждение, возражения, решение, реализация.
Именно это делает систему способной менять себя, а не только задачи.

## 9. Чего в P0 ещё нет

- UI для предложений (пока API + шаблон issue);
- автоматическая эскалация просроченных обсуждений;
- кворум 2/3 для `meta`/`charter` (сейчас фиксируется метод решения);
- проверка «у каждого инварианта есть тест» в CI (есть в тесте
  `test-proposals`, но не как отдельный шаг).
