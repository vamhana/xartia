# Продукт v0.1 «Коллектив» — решение

> Дата: 24.10.2026. Статус: принято, выполняется.
> Контекст: [roadmap.md](roadmap.md), реестр [id_2.md](../id_2.md).

---

## 1. Что мы строим

**Рабочее пространство программистского коллектива**, куда можно пригласить
человека по ссылке: он подаёт заявку, получает роль и первую задачу, делает
работу, показывает результат — и всё это видят остальные.

Это не «цивилизация 12×5» на данном этапе. Это её первый рабочий контур:
люди → роли → задачи → результат → видимый вклад. Хартия остаётся рамкой
(ротация, прозрачность, Потоки как счётчики), но продукт меряется не
соответствием Хартии, а тем, может ли новый человек начать работать в тот же
день.

## 2. Определение «можно приглашать» (invite-ready)

Продукт готов приглашать, когда выполнены **все семь** пунктов. Каждый —
бинарный, проверяется руками за 5 минут.

| № | Проверка | Сейчас |
|---|---|---|
| 1 | Публичная страница объясняет проект за 60 секунд и ведёт на форму заявки | **✓ сделано 24.10** |
| 2 | Заявка доходит до Архитектора, он принимает её в 2 клика, человек получает ID и пароль | **✓ сделано 24.10** |
| 3 | Новый участник входит и видит: свою роль, наставника, первую задачу | **✓ сделано 24.10** |
| 4 | Задача → отчёт с артефактом (PR/коммит) → ОТК → Поток, без SQL | **✓ сделано 24.10** |
| 5 | Все видят ленту «кто что сделал» и список людей с ролями | **✓ сделано 24.10** |
| 6 | Экран Шлюза: внешние продукты, деньги, расходы на серверы | ~ API есть, данных нет |
| 7 | Один домен, бэкап, health, CI на каждый PR | **✓ сделано 24.10** |

Правило: **пункт 7 не обсуждается**. Приглашать людей на систему без CI и
бэкапа — значит терять их работу при первом же сбое.

## 3. Что уже есть (проверено запуском)

- API на :3000, WebSocket на :3001, web на :5173; в k8s — `api`, `web`, `ws`,
  `worker` и данные (`postgres`, `redis`, `minio`). Логин Архитектора работает.
- 17 направлений, матрица прав (сотни строк), 32 миграции, 16 WS-каналов,
  ~50 доменных модулей (участники, задачи, планы, отчёты, ОТК, Потоки,
  мандаты, балансировка, жюри, шлюз, конструктор панелей).
- Десятки скриптовых интеграционных тестов `scripts/test-*.ts` — фактически
  регрессионная сеть, просто вне CI.
- `pnpm typecheck` по API — чисто. `typecheck:web` — 12 ошибок в 3 страницах
  (`Convergence`, `Experiments`, `Quanta`), к онбордингу отношения не имеют.

Вывод: **основа готова, витрины и онбординга не было.** Домен умеет почти всё,
но человек, пришедший с улицы, упирался в стену: заявку некому принять
(HTTP-входа в `createFromRequest` не существовало), а внутри — пустые экраны.

### Шаг 6 — CI и бэкап (сделано 24.10)

| Что | Статус |
|---|---|
| `.github/workflows/ci.yml` | джоб `static` (typecheck, tsc, vite build) + `smoke` (postgres+redis, миграции, API, 6 тестов); на GitHub — зелёный |
| `scripts/ci-local.ps1` | тот же прогон локально — **14/14 шагов зелёные** (витрина, коллектив, роль при приёме, задачи) |
| `scripts/backup.ps1 -Verify` | дамп + восстановление в отдельную БД: 232 таблицы, 15 участников — совпало |
| Бэкап в k8s | sidecar `pg-backup` в поде postgres: `pg_dump` по localhost → `/backups/db-backups`, 7 последних. Проверено: автоматический дамп через 60 с после старта, `pg_restore --list` читает 1820 записей, API после рестарта БД отвечает `db: ok` |

Почему sidecar, а не CronJob: в кластере `default-deny-all`, и под Job получает
«connection refused» от `postgres-svc` — проверено на четырёх конфигурациях
(разные лейблы, узлы, securityContext). Sidecar не выходит из пода, поэтому
сетевые политики не участвуют. Ограничение этого решения: дампы лежат на том же
диске, что и БД — для dev приемлемо, для продакшена нужна выгрузка в S3/MinIO.

## 5. Роли: минимальный набор на старте

Хартия описывает десятки ролей; для коллектива программистов на старте нужно
пять. Они уже ложатся на существующую матрицу прав.

| Роль | Что делает | Права в системе |
|---|---|---|
| **Архитектор** | владелец контура: принимает людей, задаёт направления | `FIRST_ARCHITECT` (wildcard) |
| **Куратор** | ведёт направление и очередь задач | `COUNCIL_MEMBER` |
| **Исполнитель** | берёт задачи, сдаёт отчёты | базовые `task:*`, `report:C` |
| **Ревьюер (ОТК)** | принимает/возвращает работу | `OTC` |
| **Хранитель** | архив, целостность, аудит | `VERIFICATION` / `ARCHIVE` |

Правило Хартии, которое работает уже сейчас: роль — временный мандат, а не
должность. Новый участник приходит `associated` и получает права по мере
мандатов, а не «навсегда».

**Роль выдаётся при приёме** (24.10): в форме заявки Архитектор выбирает
направление и роль из тех, что существуют в этом направлении
(`GET /roles?direction_id=`), приём вызывает `assignRole` (`S.0.01.03`).
Роль необязательна: если её нет в направлении или она конфликтует с уже
выданной, участник всё равно создаётся, а в ответе `role: null` — роль можно
выдать отдельно, не откатывая приём. Проверяется скриптом
`scripts/test-onboarding-role.ts`: регистрация → приём с ролью → вход →
паспорт показывает роль.

## 6. Как это соответствует вашей модели

| Ваша формулировка | Что это в продукте |
|---|---|
| «пополняемая группа, у каждого своя роль» | заявка → приём → мандат; матрица прав уже покрывает |
| «все всё видят и понимают, зачем» | лента активности + «кто есть кто» + roadmap внутри продукта (шаг 4) |
| «их достояние — код» | отчёт по задаче должен содержать артефакт: ссылку на PR/коммит, а не только фото (шаг 3) |
| «делают продукты для внешнего мира» | сущность «внешний продукт» над `external_transactions`/`external_assets` Шлюза (шаг 5) |
| «деньги сообща тратят на серверы» | расходы Шлюза как отдельный контур: приход → активы → инфраструктура, без конвертации в Потоки |
| «по нарастающей» | масштаб меняется числом людей и направлений, а не переписыванием продукта |

Ключевое отличие от «просто трекера»: Потоки — счётчики действий, а не
зарплата. Это позволяет приглашать людей без обещания денег и при этом честно
показывать вклад.

## 8. Что осознанно НЕ делаем в v0.1

- Мобильный клиент (42 блока, 1 файл) — заморожен.
- WebRTC-интервью как обязательный шаг онбординга: приглашение по знакомству
  не требует видеозвонка. Канал `W.2.13.01` остаётся, но не блокирует вход.
- Планетарный уровень, конвергенция, эксперименты — код есть, продукт нет;
  не трогаем, пока не работает база.
- Полноценная бухгалтерия Шлюза: только учёт, без проводок и валют.
- Автоматическая выдача ролей по заслугам: на старте роли выдаёт Архитектор.

## 10. Риски

1. **Онбординг без наставника** превращается в «разбирайся сам» — шаг 2 обязателен.
2. **Прозрачность без приватности** отпугивает: лента показывает действия, но не
   личные данные; паспорт остаётся доступен по правам.
3. **Шлюз без учёта** быстро становится «деньгами в чате» — шаг 5 нельзя
   откладывать дальше второго месяца.
4. **Пустой продукт**: если после принятия человек видит 0 задач, он уходит.
   Поэтому welcome-задача создаётся в момент приёма, а не «когда-нибудь».
