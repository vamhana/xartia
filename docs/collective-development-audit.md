# Аудит: готово ли ядро к коллективной разработке себя

**Смена критерия.** Раньше вопрос был «нет ли ошибок и дырок». Теперь
вопрос другой: **может ли сообщество менять саму систему — включая
правила обсуждения — и не разрушать её целостность?**

Это аудит не безопасности, а **мета-готовности**: способна ли XartIA
принимать идеи, фиксировать разногласия, превращать их в решение,
проводить это решение через код, тесты и документы и сохранять
совместимость при эволюции правил.

---

## 1. Пять направлений и честная оценка

| Направление | Главный вопрос | Сейчас |
|---|---|---|
| **Обсуждение** | Может ли участник предложить изменение любой функции ядра и обосновать его? | 🟡 обсуждение есть, но **вне системы** (GitHub Discussions) |
| **Коннект** | Как система обнаруживает разногласия, противоречия и молчание? | ⛔ нет объектов, дедлайнов, детектора противоречий |
| **Проектирование** | Как из обсуждения получается решение, пригодное для реализации? | ⛔ нет записи решения, кроме выборов Совета и ОТК |
| **Доработка ядра** | Как решение превращается в код, тесты и документацию? | 🟡 git/PR/CI есть, но **связи «решение → PR» нет** |
| **Эволюция** | Как менять сами правила, не ломая остальное? | ⛔ нет реестра инвариантов, версий Хартии, анализа совместимости |

**Вывод:** ядро готово **исполнять** правила, но не готово **обсуждать
и менять** их как единый процесс. Именно это надо построить до
приглашения участников.

## 2. Что уже есть (и чего это стоит)

| Есть | Где | Чего не хватает для мета-разработки |
|---|---|---|
| Сигналы → планы | `src/core/signals`, `plans` | сигнал — операционная проблема, не предложение изменить правило |
| Версии плана | `plan_versions` | версия плана ≠ версия правила/Хартии |
| Решения ОТК | `otc_decisions` | касаются задач, не core-правил |
| Выборы/ротация Совета | `council_elections`, `mandates` | нет процедуры «Совет утверждает изменение ядра» |
| Аудит | `audit_log`, `access_log` | нет записи «почему решили именно так» |
| Тесты инвариантов | `test-invariants`, `test-treasury` и др. | нет **реестра** инвариантов, с которыми сверяются изменения |
| Карта Хартии | `docs/charter-implementation-map.md` | это документ, не машиночитаемый реестр |
| Discussions | GitHub (внешний) | система не знает о предложении; нет ссылки «обсуждение → решение» |
| CONTRIBUTING | есть | описывает PR, не описывает **как менять правила** |

## 3. Пофункциональный аудит

Колонки: **замысел** / **факт** / **что можно обсуждать и менять** /
**где фиксируется** / **совместимость** / **блокер**.

### 3.1. Поток (репутация)

| | |
|---|---|
| Замысел | подтверждённый вклад; не деньги и не власть |
| Факт | `flow_transactions`, `task_flow_awards`, 1 Поток за принятую задачу |
| Обсуждаемо | формула начисления, виды вклада, отмена при пересмотре |
| Где фиксируется | только код и тест; обсуждение — во внешнем GitHub |
| Совместимость | изменение формулы ломает балансы и отчёты; нет версии правил |
| Блокер | **нет предложения/решения**, нельзя проследить, почему формула такая |

### 3.2. Задачи и ОТК

| | |
|---|---|
| Замысел | результат с артефактом, независимая проверка, критерии |
| Факт | `tasks`, `reports`, `otc_criteria`, `otc_decisions`, SLA |
| Обсуждаемо | критерии, порог SLA, кто утверждает критерии |
| Где фиксируется | `otc_criteria` (версия), `criteria_snapshot` |
| Совместимость | смена критериев влияет на исторические решения |
| Блокер | **кто и как меняет критерии** — процедуры нет |

### 3.3. Казна

| | |
|---|---|
| Замысел | пол 1.00, 3 из 5, траты на общее |
| Факт | `treasury`, подписи, операции, выкуп |
| Обсуждаемо | список общих благ, порог подписей, состав 5 мест |
| Где фиксируется | операции + подписи + аудит |
| Совместимость | изменение пола/порога — ломающее; нужна версия протокола |
| Блокер | **нет предложения и решения**, только исполнение |

### 3.4. Мандаты и Совет

| | |
|---|---|
| Замысел | срочность, ротация, отзыв |
| Факт | `mandates`, `council`, ротация 180 дней |
| Обсуждаемо | срок, квоты, дисквалификация |
| Где фиксируется | `rotations`, `council_elections` |
| Совместимость | смена срока влияет на действующие мандаты |
| Блокер | **кто утверждает смену срока** — размыто (Совет? Архитектор?) |

### 3.5. Ячейки, ёмкость, перестановка

| | |
|---|---|
| Замысел | 5×5, готовность, сигналы L0–L3 |
| Факт | `cells`, `readiness`, `capacity`, `reassignment_signals` |
| Обсуждаемо | размер, чек-лист, пороги сигналов |
| Где фиксируется | сигналы + решения |
| Совместимость | смена размера ячейки ломает дерево и наряды |
| Блокер | **нет версии «модели ячеек»** и анализа влияния |

### 3.6. Шлюз

| | |
|---|---|
| Замысел | права/деньги раздельно, идемпотентность |
| Факт | `gateway`, аудит, выручка в казну |
| Обсуждаемо | типы сделок, кто одобряет, конвертация |
| Где фиксируется | сделки + решения |
| Совместимость | новая схема конвертации меняет казну |
| Блокер | **нет связи «сделка → правило, по которому она проведена»** |

### 3.7. Документация и Хартия

| | |
|---|---|
| Замысел | Хартия — источник смысла, код — её реализация |
| Факт | `docs/charter-specs/xartia.md`, `charter-implementation-map.md` |
| Обсуждаемо | всё, включая саму карту |
| Где фиксируется | git + Discussions |
| Совместимость | версии Хартии не пронумерованы как контракт |
| Блокер | **нет машиночитаемой связи «статья → инвариант → тест»** |

### 3.8. Обсуждение и решения (мета-уровень)

| | |
|---|---|
| Замысел | можно предложить изменить **любую** функцию, включая обсуждение |
| Факт | GitHub Discussions + Telegram; решения нигде не фиксируются как объект |
| Обсуждаемо | да, но система об этом не знает |
| Где фиксируется | нигде в ядре |
| Совместимость | не проверяется |
| Блокер | **главный: нет объекта «Предложение» и «Решение»** |

## 4. Восемь разрывов, которые надо закрыть

1. **Нет предложения (RFC).** Идея живёт в чате и теряется.
2. **Нет возражений как объектов.** «Я против» не фиксируется, не
   типизируется и не закрывается.
3. **Нет решения как записи.** Нельзя восстановить: кто, когда, на
   каком основании, какие альтернативы отклонили.
4. **Нет дедлайна обсуждения.** Молчание неотличимо от согласия.
5. **Нет анализа влияния.** Изменение не обязано перечислить, какие
   функции и инварианты затронуты.
6. **Нет реестра инвариантов.** Тесты есть, но нельзя ответить «какие
   правила защищает этот тест».
7. **Нет версии Хартии как контракта.** Непонятно, какая версия правил
   действует и что считается breaking change.
8. **Мета-правила вне системы.** Даже правила обсуждения меняются
   «в GitHub», а не процедурой XartIA.

## 5. Целевой цикл

```
Идея → Предложение (draft)
     → Обсуждение (discussion, deadline)
     → Возражения (objections, типизированные)
     → Решение (decision: принято/отклонено/отложено, с обоснованием)
     → Реализация (implementing: PR, миграции, тесты)
     → Проверка совместимости (impact: инварианты, breaking?)
     → Принятие (accepted) / Откат (reverted)
```

Ключевое: это **разные события**, и каждое оставляет запись.

### Правила разногласий (предлагаемые)

| Тип возражения | Что значит | Как закрывается |
|---|---|---|
| **Фактическое** | «в коде не так, как вы описали» | автор отвечает ссылкой на код/тест |
| **Концептуальное** | «сама идея противоречит Хартии» | Совет/Архитектор выносит решение с обоснованием |
| **Совместимости** | «это сломает X, Y, Z» | обязательный анализ влияния и план миграции |

- Дедлайн обсуждения: **7 дней** (настраивается).
- Если blocking-возражений нет — «согласовано», решение фиксируется.
- Если есть — решение принимает назначенный орган (Совет направления
  или Архитектор), **письменно** объясняя, почему возражение принято
  или отклонено.
- Молчание не равно согласию для breaking changes: нужен явный кворум.

## 6. Модель данных (что добавить)

```
proposals(id, type, title, problem, proposal, alternatives,
          status, author_id, discussion_url, deadline, created_at, updated_at)
proposal_objections(id, proposal_id, author_id, kind,
                    text, status, resolution, created_at)
proposal_decisions(id, proposal_id, decided_by, method,
                   outcome, rationale, created_at)
proposal_impacts(proposal_id, invariant_id, change_kind, migration_note)
invariants(id, statement, module, test_path, since_version, status)
proposal_events(id, proposal_id, from_status, to_status, actor_id, at)
```

`type`: `module` (изменение функции), `rule` (изменение правила),
`meta` (изменение самого обсуждения/Хартии), `charter` (статья).
`meta` и `charter` требуют повышенного кворума и явного решения.

## 8. Definition of Done «можно приглашать»

Участник может **без встречи с мейнтейнером**:

1. Создать предложение изменить Поток (или ОТК, или само обсуждение).
2. Увидеть, какие инварианты и функции это затрагивает.
3. Получить возражения и ответить на них.
4. Дождаться решения по правилам (дедлайн/кворум), а не «как решит Вася».
5. Реализовать изменение, приложив тесты и миграцию.
6. Пройти проверку совместимости.
7. Увидеть запись: почему решение принято и что изменилось.

Пока этого нет — приглашение разработчиков будет просьбой «доверьтесь
мейнтейнеру», а не участием в системе.

## 9. Что это меняет в предыдущем аудите

Предыдущий аудит был аудитом **продукта**: права, деньги, ошибки.
Он остаётся полезным, но недостаточным. Главный риск теперь не «баг в
казначействе», а **невозможность легитимно изменить правило** без
разрушения доверия.

Поэтому порядок такой:
1. **P0** — предложение/возражение/решение/инварианты (этот документ).
2. Затем — приглашение первых 5–10 человек в обсуждение.
3. Затем — первые реальные изменения ядра через этот процесс.
4. И только потом — регистрация хартийцев и масштабирование.
