## 0. Назначение документа

Этот документ — самостоятельное задание на выполнение Фазы 0 проекта XartIA.

Фаза 0 должна превратить принятые архитектурные решения `DEC-01–DEC-36` в проверяемую и непротиворечивую карту реализации. Для каждого решения необходимо установить:

1. Какое именно поведение должна обеспечивать система.
2. Какие компоненты, функции, типы, таблицы, API, интерфейсы и тесты уже существуют.
3. Что из существующего кода действительно обеспечивает целевое поведение, а что лишь частично похоже на него.
4. Какие разрывы, противоречия, незафиксированные контракты и тестовые пробелы остаются.
5. Какие существующие ID нужно изменить и какие новые ID могут понадобиться.
6. От каких решений и компонентов зависит каждая последующая фаза.
7. По каким проверяемым критериям можно будет принять результат каждой последующей фазы.

**Фаза 0 не реализует функциональность.** Её результат — подтверждённая архитектурная карта, полный GAP-реестр, карта зависимостей и подготовленная декомпозиция следующих фаз.

## 3. Рабочая процедура аудита

Для каждого `DEC-01–DEC-36` выполнить одинаковую процедуру.

### Шаг 1. Зафиксировать требование

Перенести целевую формулировку DEC из родительского документа без смыслового изменения. Разложить её на атомарные проверяемые утверждения: актор, действие, объект, условия, полномочия, состояние до/после, исключения и история.

### Шаг 2. Найти фактическую реализацию

Для каждого утверждения найти:

- существующий ID компонента;
- точный путь файла из `id_2.md`;
- точную функцию/метод/тип/интерфейс в кодовом слепке;
- связанные таблицы и ограничения БД;
- API route/DTO и UI, если они затронуты;
- тесты, реально покрывающие именно это поведение.

Указывать line/heading/ID-маркер в кодовом слепке или точную сигнатуру функции. Если подтверждение отсутствует, прямо писать, что в предоставленном срезе оно не найдено. Не делать вывод «механизма нет» только потому, что он не упомянут в кратком описании реестра.

### Шаг 3. Определить статус покрытия

Использовать один из статусов:

- `реализовано` — целевое поведение подтверждено кодом и соответствующим тестом;
- `частично` — существует базовый механизм, но часть целевой семантики не обеспечена;
- `отсутствует` — после проверки релевантных путей и зависимостей подтверждено отсутствие механизма;
- `противоречит целевой модели` — существующая реализация непосредственно нарушает принятое DEC;
- `нужно подтверждение` — по имеющимся данным нельзя надёжно установить состояние или требуется дополнительное архитектурное решение.

Дополнительно указывать уверенность (`высокая`, `средняя`, `низкая`) и причину ограничения. Не повышать статус до `реализовано` только на основании описания в `id_2.md`.

### Шаг 4. Описать GAP и последствия

Для каждого расхождения указать:

- ожидаемое поведение;
- фактическое поведение;
- точные доказательства;
- последствия для пользователя, целостности данных, безопасности, прав, истории или смежных процессов;
- минимально необходимое изменение целевой модели/кода;
- смежные механизмы, которые нельзя сломать;
- негативный сценарий, который должен быть запрещён.

### Шаг 5. Назначить фазу и зависимости

Проверить, что GAP действительно относится к назначенной фазе. Если он блокирует несколько фаз, указать первичную фазу-владельца и зависимые фазы. Не переносить проблему в более позднюю фазу только ради удобства, если без неё предыдущая фаза будет небезопасна.

### Шаг 6. Зафиксировать тестовую доказательность

Разделять:

- существующий тест, который реально проверяет правило;
- существующий тест, который проверяет лишь часть поведения;
- тест, который сейчас закрепляет старую/противоречащую модель;
- отсутствующий сценарий, который требуется добавить в будущей фазе.

Не утверждать, что тест проходит, если он только прочитан в кодовом слепке. В Фазе 0 тесты не запускаются и не изменяются.

Проверить, что постоянная ячейка не смешана с временной конфигурацией смены. Отдельно проверить четыре смены в локальные сутки, версии ростера, состав 5 рабочих участников + координатор, неполные ростеры, готовность под конкретную работу, доступность людей, подтверждение координатора и историю замены участника.

### 5.3. План, задача и подтверждения

Проверить границы между задачей и планом, дневным нарядом и личным планом, публикацией и подтверждением, версией плана и версией ростера. Определить, какие подтверждения относятся к точной версии и какие действия должны требовать повторного подтверждения.

### 5.4. ОТК, профессиональный паспорт и Поток

Проверить всю цепочку: конкретная смена → результат → независимый проверяющий → критерии/атомы → решение ОТК → passport failure/suspension → retraining/reassessment → учительская педагогическая оценка → правило Потока за день провала. Не подменять day-level правило текущим task-level начислением.

### 5.5. Сигналы и handover

Проверить, что signal response, escalation, handover acceptance и передача операционной ответственности — не одно и то же действие. Установить, где должна храниться трасса основного получателя, резервного адресата, сроков, подтверждений и закрытия отправителем.

### 5.6. История и версионирование

Проверить, где достаточно snapshot/version records, где требуется append-only event, где обновление текущей сущности допустимо и какие данные нельзя удалять/переписывать. Не предлагать полный Event Sourcing как решение по умолчанию.

### 5.7. Каталоги, компетенции и уровни

Проверить, что XSK, старый каталог, CYB.ATOM, уровень 0–9, G0–G5, Permit, недельный мандат, CoordinatorProfile, TeachingCapability и TeamCapability не подменяют друг друга. | XAD-04 | Один личный дневной план сохраняется на участника и его локальную дату. Разные смены отражаются разными блоками с `shift_id`/assignment reference внутри этого плана. | Не создаёт второй личный план и поддерживает несколько смен в один день; DEC-18. |
| XAD-05 | Недельный мандат координатора длится ровно 168 часов от момента принятия участником; он активируется только после явного согласия назначенного человека. | Точная длительность не зависит от DST; ответственность нельзя незаметно навязать или смешать с утверждением ростера. |
| XAD-06 | Кандидат координатора проходит жёсткий паспортный eligibility gate. Среди пригодных выбирается наименьшая проверяемая пересекающаяся координационная нагрузка; затем — самый давний момент предыдущего назначения; последняя ничья разрешается стабильным ID. | Прозрачная лексикографическая политика без придуманных весов/порогов и без замены компетенции популярностью. |
| XAD-07 | `CoordinatorCapabilityProfile` — вычисляемая версиями паспорта проекция подтверждённых атомов/допусков, а не второй независимый паспорт или ручной список компетенций. | Один источник компетенции для Matching, Coordinator и OTK. |
| XAD-08 | Readiness проверяется для конкретной смены и конкретного наряда. Неполный ростер допустим, когда все обязательные атомы/позиции фактических задач покрыты; численность сама по себе не является gate. | Выполняет DEC-12 и не подменяет Matching. |
| XAD-09 | Запоздавший worker не запускает смену автоматически. Координатор может вручную начать её после планового времени, если readiness пройдена и текущий момент ещё внутри запланированного интервала. После окончания интервала запуск запрещён без нового согласованного интервала. | Повторяемое расписание не должно само совершать производственное действие; нет скрытого grace period/автопродления. |
| XAD-10 | Handover состоит из отдельно принимаемых позиций. Получение пакета/контекста не передаёт ответственность за позицию. Непринятая обязательная позиция остаётся у передающего; при наступлении начала принимающей смены включается заранее назначенный резервный маршрут. | Прямо реализует DEC-19/20; не переносит ответственность на основании факта отправки. |
| XAD-11 | Истечение мандата не аннулирует уже возникшее узкое обязательство завершить передачу, но не продлевает общие координационные полномочия. | Разводит DEC-02 и DEC-19 без автоматического продления мандата. |
| XAD-12 | Провал атома удерживает весь положительный Поток участника за локальный день до финального урегулирования; день определяется timezone личного дневного плана, сохранённым в записи. Поздний провал после выплаты создаёт компенсирующее событие, не удаляя прежнюю транзакцию. | Исполняет DEC-27, сохраняет идемпотентность и историю. |
| XAD-13 | `LongTermTask` имеет immutable `TaskRevision`; отдельный `ImplementationCycle` связывает одну ревизию с общим планом направления и собственным root `package`. Один `Plan` может содержать несколько циклов; дерево `package/deliverable` ограничено одним `plan_id`, `direction_id` и `implementation_cycle_id`. | Сохраняет семантику существующего direction-wide `Plan` и same-plan guard; не превращает общий план направления в план одной задачи. |
| XAD-14 | Родительский результат проверяется отдельным `ParentOutcomeReview`, а не назначением `package` и не фиктивным deliverable. | Соблюдает DEC-29/30 и запрет назначения package. |
| XAD-15 | Незавершённые deliverables не перемещаются между планами задним числом. Новый цикл создаёт successor deliverables со ссылкой на predecessor; принятые результаты можно повторно использовать только по явному решению о применимости без повторного Потока. | Защищает историю assignment/OTK/Flow и не переписывает старый цикл. |
| XAD-16 | TeamCapability case создаётся на один `ImplementationCycle`, который однозначно указывает `LongTermTask + TaskRevision`. Версия конфигурации ссылается на одну или несколько точных версий ростера и сохраняет снимок ролей и условий взаимодействия. | Одна редакция задачи может исполняться в нескольких циклах с разными конфигурациями; оценку нельзя переносить между ними. |
| XAD-17 | `TeamCapabilityAssessment.level` — самостоятельное целостное заключение assessor; `criteria_scores` — отдельная детализация. Они не усредняются автоматически, порог допуска не создаётся без утверждённых критериев. | Нет принятой формулы/весов; не изобретаем математику оценки. |
| XAD-18 | Старые TeamCapability assessments без доказуемого состава получают `legacy_unbound`, остаются исторически читаемыми и не участвуют в eligibility/matching. | Не создаёт фиктивную историческую конфигурацию. |
| XAD-19 | Team-level события ведутся отдельно от личного `passport_history_events`. Доступ к личному паспорту не следует автоматически из членства в команде. | Не выдаёт событие о команде за индивидуальное паспортное изменение. |
| XAD-20 | Переход выполняется expand–migrate–switch–contract: новые структуры добавляются, legacy backfill маркируется, новый write path становится каноническим, старые read API могут обслуживаться адаптером, старые write пути отключаются только после доказанного переключения callers. | Нет dual-write двух конкурирующих источников истины; обеспечивает сохранность legacy. |

### 14.4. Остаточные решения, которые не закрываются техническим выбором

1. Кворум, правила голосования, Жюри/Коннект, правопреемство упразднённого Совета и аварийные полномочия должны соответствовать утверждённым процедурам Хартии.
2. Педагогические критерии и распределение D11↔D14 не устанавливаются этой фазовой серией.
3. Release baseline фактической локальной рабочей ветки, резервное восстановление production и формальная приёмка релиза подтверждаются перед Фазой 10.
4. Неизвестная историческая принадлежность, отсутствующий timezone, недоказанный OTK или неидентифицированный Council owner не заполняются эвристикой; используется явный `unresolved`/`legacy_unbound` и блокировка затронутого действия.

### 14.5. Как использовать версии фаз

В этой редакции X.0.01.41.00 фиксирует межфазовое решение; Фазы 1–10 получают соответствующие уточнения контрактов.
